# HTML Doc

仕様書・設計書・計画資料・プロジェクト説明資料などを **読みやすい HTML ファイル** として書き出すスキル。表紙・目次・章単位の改ページを備え、PDF 印刷でページ単位でも見やすい。

CSS はプラグイン同梱の `assets/template.html` に固定されており、生成のたびに CSS を書かない。本文は `assets/components.md` のカタログ部品（フロー図・タイムライン・ガント・カード・表など）を組み合わせ、**フロー・スケジュール・体制・数値はなるべく視覚的に表現** する。

反復生成と長大ドキュメントに耐えるため、HTML の組み立ては **Codex の built-in `worker` サブエージェント** に委任し、生成 HTML 全文を親 Codex の会話履歴に残さない。

## 1. 発動条件と非発動条件

発動するとき（以下のいずれかをユーザーが明示的に指示したターンのみ）:

- 「HTML でドキュメント / 仕様書 / 設計書 / 計画資料 / 説明資料を作って・出して・書き出して」
- 「html-doc で」「html-doc 発動」
- 「この内容を HTML にして」「HTML ドキュメントにまとめて」

発動しないとき（以下では絶対に発動しない）:

- 他スキルからの連鎖発動
- 「仕様をまとめて」「ドキュメントを書いて」と言っただけのターン（Markdown 提示で良い）
- 調査・読み取り・質問応答・コード実装だけで完結するターン
- 実行プランの HTML 化（`html-plan` スキルの領分）

迷ったら発動しない。ユーザーが明示的に指示したかどうかが唯一の判断基準。

## 2. 動作モデル（サブエージェント委任型）

```
[親 Codex]                            [built-in worker サブエージェント]
 │ ① ドキュメント化する内容を特定
 │ ② メタ情報(タイトル, 種別, 版数等)を決定
 │ ③ 出力先とファイル名を決定
 │ ④ サブエージェントを spawn ────► プロンプト受領
 │                                    │ ⑤ assets/template.html と
 │                                    │    assets/components.md を Read
 │                                    │ ⑥ メタ置換 + {{BODY}} を部品で組み立て
 │                                    │ ⑦ 出力先へ Write
 │ ⑧ 保存パスだけ受け取る ◄────────── 戻り値: 保存パス(短文)
 │ ⑨ ユーザーに保存パスを伝える
```

委任する理由:

- 生成 HTML 全文（数 KB 〜 数十 KB）を親会話履歴に残さない
- 反復的な再生成で親コンテキストが累積しない
- 長大なドキュメントでもメイン推論を圧迫しない

**親 Codex がやってはいけないこと**: 自分で `template.html` / `components.md` を Read したり、自分で Write を呼んだりしない。必ず built-in `worker` サブエージェントに委任する。

## 3. 親 Codex の手順

### 3.1 入力の特定

入力: 直近の会話履歴
出力: HTML 化対象のドキュメント本文

優先順位:

1. ユーザーがこのターンで提示した文章・ファイル・会話中の合意内容
2. 会話中で直近にまとめた仕様・計画・説明の本文
3. 見当たらなければ「どの内容を HTML ドキュメント化しますか?」と 1 ターン 1 判断で確認

### 3.2 メタ情報の決定

入力: ユーザー発話・会話内容
出力: `TITLE`, `SUBTITLE`, `DOC_TYPE`, `VERSION`, `DATE`, `AUTHOR`

- TITLE: ドキュメントタイトルを 1 行で
- SUBTITLE: サブタイトル（無ければ空）
- DOC_TYPE: 文書種別（例: 仕様書 / 設計書 / 計画資料 / 説明資料 / 手順書 / 提案書）
- VERSION: 版数（不明なら "v1.0"）
- DATE: 本日（`YYYY-MM-DD`）
- AUTHOR: 作成者（指定が無ければ "-"）

### 3.3 出力先とファイル名の決定

入力: ユーザー指定（任意）、ドキュメント主題、本日日付
出力: `OUTPUT_PATH`

- 配置先: **ユーザー指定を最優先**。指定が無ければリポジトリルート相対 `./docs/`（無ければサブエージェントが作成）
- ファイル名: `doc-YYYY-MM-DD-{slug}.html`
  - `slug` は kebab-case、英数字とハイフンのみ、最大 40 文字。日本語タイトルは英訳して kebab-case 化
- **反復生成時の上書きルール**: 同一日同 slug は上書き。slug が変われば別ファイルとして併存
- 「別ファイルとして残して」と言われた場合のみ `-2`, `-3` を付与

### 3.4 テンプレートとカタログの絶対パス解決

入力: SKILL.md の絶対パス
出力: `TEMPLATE_ABS_PATH`, `CATALOG_ABS_PATH`

参照ファイルはこのプラグインの `assets/` にある。

- `assets/template.html` — HTML 外枠 + 全コンポーネント CSS
- `assets/components.md` — 本文に使える部品のカタログ

解決順（上から優先）:

1. 環境変数 `CODEX_PLUGIN_ROOT` が定義されていれば → `${CODEX_PLUGIN_ROOT}/assets/...`
2. SKILL.md 自身の絶対パスから導出 → `<SKILL.md と同じディレクトリ>/../../assets/...`
3. 最後の手段として `find ~/.codex -path '*html-doc-renderer/assets/template.html' -print -quit` 等で探索

### 3.5 サブエージェントへの委任

built-in `worker` サブエージェントを 1 つ spawn する。プロンプトは次のテンプレートに揃える。

```
あなたは「html-doc」スキルのレンダリング担当サブエージェントです。
親 Codex のメインコンテキストを汚さないため、HTML の組み立てと書き出しを引き受けます。

## やること
1. テンプレートを Read（絶対パス）: {TEMPLATE_ABS_PATH}
2. コンポーネントカタログを Read（絶対パス）: {CATALOG_ABS_PATH}
3. 下記「ドキュメント本文」を章立てし、テンプレート内のプレースホルダを置換
4. {{BODY}} はカタログの部品だけで組み立てる
5. 出力先へ Write: {OUTPUT_PATH}
6. 戻り値は「保存パス（と必要なら 1〜2 行のサマリ）だけ」。HTML 本文は絶対に出力に含めないこと

## プレースホルダ対応
- {{TITLE}}      {TITLE}
- {{SUBTITLE}}   {SUBTITLE}（空なら空文字で置換）
- {{DOC_TYPE}}   {DOC_TYPE}
- {{VERSION}}    {VERSION}
- {{DATE}}       {DATE}
- {{AUTHOR}}     {AUTHOR}
- {{TOC}}        <li><a href="#sec-N">章タイトル</a></li> を章の数だけ。
                 テンプレート内に {{TOC}} は 2 箇所ある（印刷用目次・画面用サイドバー）。両方に同じ内容を入れる
- {{BODY}}       本文 HTML 断片（下記の組み立て方針に従う）
- {{META}}       フッター用の補足（例: "Generated by html-doc skill"）

## {{BODY}} の組み立て方針
- 章は <section class="chapter" id="sec-N"><h2 class="chapter-heading">N. タイトル</h2>...</section>。
  id は {{TOC}} のアンカーと一致させる。章番号はタイトル文字列に含める
- 印刷時は章ごとに改ページされる。1 章が A4 で 1〜3 ページに収まる粒度に章を分ける
- **視覚優先**: フロー・手順はフロー図(.flow)や手順リスト(.procedure-steps)、
  スケジュールはタイムライン(.timeline)やガント(.gantt)、体制・機能一覧はカード(.card-grid)、
  規模・KPI は数値ハイライト(.stat-grid)、比較・一覧は表(.doc-table)で表現する。
  段落だけが続く章を作らない
- 注意点・制約はコールアウト(.callout--info/--warning/--danger/--success)で目立たせる
- 仕様書・計画資料では改訂履歴(.revision-table)の章を末尾に置く（履歴情報が無ければ初版 1 行）
- 使える部品・マークアップはカタログ（components.md）に厳密に従う。カタログに無いクラスを発明しない

## 制約
- テンプレ内の <style> 領域は改変しない（プレースホルダ部分のみ置換）
- HTML エスケープを徹底（<, >, &, ", ' を実体参照に）。`<code>` 内も同様
- 外部 CDN や <script> は追加しない
- ドキュメント内容を要約・脚色しない（忠実に構成し直すのは可、内容の改変は不可）
- 出力ディレクトリが無ければ作成
- 最終応答は「保存パス: {OUTPUT_PATH}」のみ（HTML 全文を返さない）

## メタ情報
- OUTPUT_PATH: {OUTPUT_PATH}

## ドキュメント本文（HTML 化する対象）
---
{DOC_BODY}
---
```

差し込む値:

- `{TEMPLATE_ABS_PATH}` / `{CATALOG_ABS_PATH}` — 3.4 で解決した絶対パス
- `{TITLE}` / `{SUBTITLE}` / `{DOC_TYPE}` / `{VERSION}` / `{DATE}` / `{AUTHOR}` — 3.2 で決めた値
- `{OUTPUT_PATH}` — 3.3 で決めた値
- `{DOC_BODY}` — 3.1 で特定した内容を **そのまま** 貼る（要約しない）

### 3.6 戻り値の取り扱い

サブエージェントは「保存パス」と短いサマリだけ返してくる。親 Codex はこれをユーザーに伝えるだけにする。

良い報告例:

> `./docs/doc-2026-06-05-payment-spec.html` に書き出しました。ブラウザで開き、PDF にする場合は印刷から「PDF に保存」してください。

## 4. 反復修正への対応

1. まず会話上でドキュメント内容を更新する
2. 「もう一度 HTML にして」と言われたら、最新の内容を持って 3.5 のサブエージェント spawn を再実行
3. 同日同 slug のファイルは上書きする（3.3 の上書きルール）

サブエージェントは毎回新規に spawn して構わない（状態を持たない）。

## 5. 出力ルール

- 応答は保存パス（と必要なら 1〜2 行のサマリ）だけ
- 生成 HTML の中身は会話に貼り直さない
- ドキュメント本文を再掲しない
- サブエージェントが返したメッセージを長々と転記しない
- 出力先はユーザー指定パス、または `./docs/` 配下。リポジトリ外には書かない（ユーザーが明示指定した場合を除く）

## 6. 禁止事項

- **親 Codex が直接 `template.html` / `components.md` を Read したり、Write で HTML を書き出すこと**（必ず built-in `worker` サブエージェント経由）
- サブエージェントの戻り値として HTML 全文を親会話に持ち帰ること
- HTML 内への `<script>` 埋め込み、`onload` などのイベントハンドラ
- 外部 CDN（Google Fonts、Tailwind CDN、Mermaid CDN など）への参照
- 自動発動、ユーザーが明示指示していないのに先回りで HTML 出力すること
- ドキュメント内容を勝手に書き換える / 追加で考察を入れる（忠実な可視化に徹する）
