# HTML Plan

合意済みの実行プランを **読みやすい HTML ファイル** として `./plans/` 配下に書き出すスキル。目次・TL;DR・メタチップ・ファイル変更表・必読ブロック・折りたたみステップを備える。

ユーザーは生成された HTML を見ながら、質問・修正依頼・確認プロンプトを繰り返す。大規模リファクタのプランにも使われる。反復生成と長大プランに耐えるため、HTML の組み立ては **Codex の built-in `worker` サブエージェント** に委任し、生成 HTML 全文を親 Codex の会話履歴に残さない。

プレースホルダ仕様は 3.5 のサブエージェント向けプロンプトテンプレートに含まれている(サブエージェント自身が読む契約書として扱う)。

## 1. 発動条件と非発動条件

発動するとき(以下のいずれかをユーザーが明示的に指示したターンのみ):

- 「HTML でプランを出して / 書き出して / 保存して」
- 「html-plan で」「html-plan 発動」
- 「いまの計画を HTML にして」「プランを HTML ファイルにして」
- 上記に明確に類する表現

発動しないとき(以下では絶対に発動しない):

- プランを立てた直後の自動連動
- 他スキルからの連鎖発動
- ユーザーが「プランを立てて」「計画して」と言っただけのターン(プラン提示は Markdown のままで良い)
- 調査・読み取り・質問応答だけで完結するターン

迷ったら発動しない。ユーザーが明示的に指示したかどうかが唯一の判断基準。

## 2. 動作モデル(サブエージェント委任型)

このスキルは **親 Codex → built-in `worker` サブエージェント** の二段構成で動く。

```
[親 Codex]                            [built-in worker サブエージェント]
 │ ① 最新の合意プランを特定
 │ ② メタ情報(repo, branch, 日付)を取得
 │ ③ ファイル名を決定
 │ ④ サブエージェントを spawn ────► プロンプト受領
 │                                    │ ⑤ assets/template.html を Read
 │                                    │ ⑥ プレースホルダ置換
 │                                    │ ⑦ ./plans/... へ Write
 │ ⑧ 保存パスだけ受け取る ◄────────── 戻り値: 保存パス(短文)
 │ ⑨ ユーザーに保存パスを伝える
```

委任する理由:

- 生成 HTML 全文(数 KB 〜 数十 KB)を親会話履歴に残さない
- 反復的な再生成(質問→プラン更新→再 HTML 化)で親コンテキストが累積しない
- 大規模リファクタの長大なプランでもメイン推論を圧迫しない

**親 Codex がやってはいけないこと**: 自分で `template.html` を Read したり、自分で Write を呼んだりしない。必ず built-in `worker` サブエージェントに委任する(理由: そうしないと HTML 全文が親履歴に残るため)。

## 3. 親 Codex の手順

### 3.1 入力(合意済みプラン)の特定

入力: 直近の会話履歴
出力: HTML 化対象のプラン本文

次の優先順位で「現在のプラン」を特定する。

1. 直前のターンに承認されたプラン本文
2. 会話中で直近に合意した実装計画(要点ブロック、TODO、ユーザーが OK を出した提案など)
3. それも見当たらない場合は、ユーザーに「どのプランを HTML 化しますか?」と 1 ターン 1 判断で確認

### 3.2 メタ情報の取得

入力: 作業中リポジトリ
出力: `REPO`, `BRANCH`, 日付(`YYYY-MM-DD`)

- リポジトリ名: `git remote get-url origin` の末尾(`org/repo`)、取れなければ空
- ブランチ名: `git branch --show-current`、取れなければ空
- 日付: 本日(`YYYY-MM-DD`)

### 3.3 ファイル名規則

入力: プラン主題、本日日付
出力: `./plans/plan-YYYY-MM-DD-{slug}.html`

- 配置先: 作業中リポジトリのルート相対 `./plans/`(無ければサブエージェントが作成する)
- ファイル名: `plan-YYYY-MM-DD-{slug}.html`
  - `slug` は kebab-case、英数字とハイフンのみ、最大 40 文字
  - 日本語タイトルは英訳または音写して kebab-case 化
- **反復生成時の上書きルール**: 同一日に **同じ slug** のファイルがあれば **上書き** する(プランの修正→再生成のため)。slug が変われば別ファイルとして併存
- 明示的に「別ファイルとして残して」と言われた場合のみ `-2`, `-3` を末尾に付与

### 3.4 テンプレートファイルの絶対パス解決

サブエージェントは親 Codex と独立したワーキングディレクトリを持つ可能性があるため、テンプレートは **絶対パス** で渡す。

テンプレートは、このプラグインの **`assets/template.html`** に置かれている。

解決手順(上から優先):

1. 環境変数 `CODEX_PLUGIN_ROOT` が定義されていれば → `${CODEX_PLUGIN_ROOT}/assets/template.html`
2. SKILL.md 自身の絶対パスから導出 → `<SKILL.md と同じディレクトリ>/../../assets/template.html`
3. それも不明な場合のみ最後の手段として `find ~/.codex -path '*html-plan-renderer/assets/template.html' -print -quit` 等で探索

この絶対パス(以下 `{TEMPLATE_ABS_PATH}`)を 3.5 でサブエージェントに渡す。

```
## やること
1. テンプレートを Read(絶対パス): {TEMPLATE_ABS_PATH}
2. 下記「プラン本文」から各セクションを抽出し、テンプレート内のプレースホルダを置換
3. 出力先へ Write(リポジトリルート相対): {OUTPUT_PATH}
4. 戻り値は「保存パス(と必要なら 1〜2 行のサマリ)だけ」。HTML 本文は絶対に出力に含めないこと

## プレースホルダ対応
### 基本メタ
- {{TITLE}}                プラン主題を 1 行で
- {{GENERATED_AT_ISO}}     ISO 8601(例: 2026-05-12T10:30:00+09:00)
- {{GENERATED_AT}}         人間向け表記(例: 2026-05-12 10:30)
- {{REPO}}                 {REPO} を埋める(空なら "-")
- {{BRANCH}}               {BRANCH} を埋める(空なら "-")
- {{TOC}}                  <li><a href="#anchor">章タイトル</a></li> を必要数。各 <section> の id と一致させる
- {{META}}                 フッター用の補足(例: "skill: html-plan / branch: foo")

### TL;DR(冒頭バナー、最も目立つ場所)
- {{TLDR_3_LINES}}         3 行以内の超要約。「何を・なぜ・どんな成果になるか」を 1 文ずつ
- {{TLDR_MAX_IMPACT}}      最も影響の大きい変更点を 1 文(壊れたら誰が困るかの観点)
- {{TLDR_REVIEW_FOCUS}}    レビューで最初に見るべき箇所(例: "ファイル X の関数 Y / マイグレーション順序")

### 全体メタチップ(影響・所要時間・ロールバック)
- {{IMPACT_LEVEL}}         "high" / "med" / "low" のいずれか(チップの色分け用)
- {{IMPACT_SCOPE}}         影響範囲を短句で(例: "認証フロー全体", "管理画面のみ")
- {{ESTIMATED_TIME}}       推定実装時間(例: "2〜3 時間", "半日")
- {{ROLLBACK_LEVEL}}       "high"(困難)/ "med" / "low"(容易) のいずれか
- {{ROLLBACK_DIFFICULTY}}  ロールバック容易度の短句(例: "revert で完結", "DB マイグレーション要逆行")

### 要点ブロック
- {{SUMMARY_WHAT}}         要点: 何を
- {{SUMMARY_WHY}}          要点: なぜ
- {{SUMMARY_HOW}}          要点: どう
- {{SUMMARY_SIDE_EFFECTS}} 要点: 副作用と影響範囲
- {{SUMMARY_OUT_OF_SCOPE}} 要点: スコープ外

### 本文
- {{CONTEXT}}              背景/目的の本文(<p> タグで段落化)
- {{FILES_TABLE}}          下記「ファイル変更行の書式」参照
- {{MUST_READ}}            レビュー時の重点ポイント。<div class="must-read">...</div> のブロックを 1〜3 個。
                            各ブロックには「該当箇所のパス・関数名」「気をつけて読むべき理由」を含める
- {{STEPS}}                下記「ステップ行の書式」参照
- {{VERIFICATION}}         <li>検証項目</li> を必要数(チェック記号 ☐ は CSS が付ける)

## ファイル変更行の書式
```
<tr>
  <td class="path"><code>path/to/file.ts</code></td>
  <td class="op" data-op="add|edit|delete">add|edit|delete</td>
  <td class="size" data-size="S|M|L">S|M|L</td>
  <td class="risk" data-risk="low|med|high">低|中|高</td>
  <td>1 行サマリ</td>
</tr>
```
- 規模(size): S = 〜30 行 / M = 30〜200 行 / L = 200 行以上
- リスク(risk): 既存呼び出し元が多い・本番影響あり・ロールバック困難 のいずれかで "high" を、純粋追加や独立モジュールは "low"

## ステップ行の書式(<details> で折りたたみ可能)
```
<li>
  <details>
    <summary>ステップタイトル(動詞で始める)</summary>
    <div class="step-goal">目的: 〜 / 完了条件: 〜</div>
    <div class="step-detail">
      <p>詳細な手順や注意点</p>
    </div>
  </details>
</li>
```
- summary は短く(1 行)、詳細は details の中。これにより冒頭スキャン時はタイトルだけ見える

## 制約
- テンプレ内の <style> 領域は改変しない(プレースホルダ部分のみ置換)
- HTML エスケープを徹底(<, >, &, ", ' を実体参照に)。`<code>` 内も同様
- 外部 CDN や <script> は追加しない
- 抽出時にプラン内容を要約・脚色しない(忠実に転記)
- 出力ディレクトリが無ければ作成
- 最終応答は「保存パス: ./plans/xxxx.html」のみ(HTML 全文を返さない)
- {{MUST_READ}} に該当するレビュー重点ポイントがプランに無い場合は、要点ブロックから推定できる注意点(副作用・スコープ境界・破壊的変更)を 1 つ抽出して書く。全く無ければ「特記なし」とだけ書いた must-read ブロックを 1 つ置く

## メタ情報
- REPO: {REPO}
- BRANCH: {BRANCH}
- OUTPUT_PATH: {OUTPUT_PATH}

## プラン本文(忠実に HTML 化する対象)
---
{PLAN_BODY}
---
```

差し込む値:

- `{TEMPLATE_ABS_PATH}` — 3.4 で解決したテンプレートの絶対パス
- `{REPO}` / `{BRANCH}` / `{OUTPUT_PATH}` — 3.2 / 3.3 で求めた値
- `{PLAN_BODY}` — 3.1 で特定した合意済みプラン本文を **そのまま** 貼る(要約しない)

### 3.6 戻り値の取り扱い

サブエージェントは「保存パス」と短いサマリだけ返してくる。親 Codex はこれをユーザーに伝えるだけにする。

良い報告例:

> `./plans/plan-2026-05-12-add-html-plan-skill.html` に書き出しました。ブラウザで開いてご確認ください。

悪い報告例:

- 生成された HTML の中身を会話に貼り直す
- プラン本文を再掲する
- サブエージェントが返した説明を長々と転記する

## 4. 反復的なプラン修正への対応

ユーザーは HTML を見ながら以下を行う想定:

- 「ここの章を書き換えて」「ステップ 3 を分割して」など部分修正
- 「副作用に X を追加して」など要点ブロックの修正
- 「もう一度 HTML にして」と再生成

このとき親 Codex は:

1. まず会話上でプラン本文を更新する(要点ブロックや TODO を最新化)
2. 「もう一度 HTML にして」と言われたら、最新のプラン本文を持って 3.5 のサブエージェント spawn を再実行
3. 同日同 slug のファイルは上書きする(3.3 の上書きルール)

サブエージェントは毎回新規に spawn して構わない(状態を持たない)。親会話には HTML 全文が残らないため、何度反復しても親コンテキストは膨れない。

## 5. 出力ルール

- 応答は保存パス(と必要なら 1〜2 行のサマリ)だけ
- 生成 HTML の中身は会話に貼り直さない
- プラン本文を再掲しない
- サブエージェントが返したメッセージを長々と転記しない
- 出力先は必ず `./plans/` 配下。リポジトリ外には書かない

## 6. 禁止事項

- **親 Codex が直接 `template.html` を Read したり、Write で HTML を書き出すこと**(必ず built-in `worker` サブエージェント経由)
- サブエージェントの戻り値として HTML 全文を親会話に持ち帰ること
- `./plans/` 以外への HTML 書き込み
- HTML 内への `<script>` 埋め込み、`onload` などのイベントハンドラ
- 外部 CDN(Google Fonts、Tailwind CDN、Mermaid CDN など)への参照
- プランを立てた直後や他スキル発動に紐づく自動発動
- ユーザーが明示指示していないのに先回りで HTML 出力すること
- プラン内容を勝手に書き換える / 追加で考察を入れる(忠実な可視化に徹する)

## 7. 大規模リファクタへの配慮

長大なプランでも 1 枚物の HTML として出力する(初期版)。サブエージェント側でテンプレ置換するため、親には HTML 全文が戻らない。

将来必要になったら章単位の分割出力も検討するが、最初は導入しない(早すぎる抽象化を避けるため)。ユーザーから「分割して出して」と明示要望が出た時点で追加する。
