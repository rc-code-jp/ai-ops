# CLAUDE.md / AGENTS.md レビューチェックリスト

ステップ 2 の 10 観点レビューで使用する詳細基準。

---

## 1. 役割分離

### チェック項目
- [ ] 毎回読む価値がある内容だけに絞られている
- [ ] 特定タスク専用の長い手順（10 行超）が混ざっていない
- [ ] Skill / rules / subagent / 別ドキュメントに逃がすべき内容が残っていない

### 良い状態
- 常時守る制約、作業前提、完了条件だけがある
- 詳細なレビュー手順や特定技術の手順は別スキルに分離されている

### NG 例
- 特定フレームワークの詳細実装手順を長々と書く
- 毎回は不要な背景説明や設計思想が大量にある
- 特定の PR テンプレートや Markdown フォーマットが全文記載されている

---

## 2. 指示の具体性

### チェック項目
- [ ] 指示が具体的な行動として書かれている
- [ ] 曖昧語（「適切に」「丁寧に」「必要に応じて」「きれいに」）に依存していない
- [ ] 誰が読んでも同じ行動を取りやすい

### 良い状態の例
- 「変更後は `npm test` と `npm run lint` を実行する」
- 「新規依存追加は承認が必要」
- 「API 変更時は docs/ 配下も更新する」
- 「コミットメッセージは Conventional Commits 形式で書く」

### NG 例
- 「丁寧に対応する」
- 「必要に応じて確認する」
- 「適切にテストする」
- 「きれいなコードを書く」
- 「品質を保つ」

### 曖昧語の改善パターン

| 曖昧語 | 改善例 |
|--------|--------|
| 適切にテストする | `npm test` を実行し全件パスを確認する |
| 必要に応じて確認する | API 変更時は `docs/api.md` を更新する |
| 丁寧に対応する | エラー時は原因と対処を報告する |
| きれいなコードを書く | ESLint ルールに従い、警告 0 で通す |
| 品質を保つ | CI の全チェックがパスした状態で報告する |

## 3. 検証可能性

### チェック項目
- [ ] ルールの遵守可否を後から確認できる
- [ ] 成功条件・完了条件（Done の定義）が明記されている
- [ ] 実行すべきコマンドが具体的に書かれている
- [ ] 変更時に必ず更新するファイルやチェック項目がある

### 良い状態
- Done の定義: 「テスト全件パス + lint エラー 0 + 型チェック通過」
- 実行コマンド: `npm test && npm run lint && npm run typecheck`
- 更新ルール: 「API エンドポイント変更時は `openapi.yaml` も更新する」

### NG 例
- 完了条件がなく「終わったら報告」だけ
- 品質をどう確認するか不明
- 「テストを書く」とあるが何を確認するか未定義

## 4. スコープ設計

### チェック項目
- [ ] グローバル / リポジトリ / サブディレクトリの責務分離ができている
- [ ] 個人設定とチーム共通設定が混ざっていない
- [ ] 局所ルールを上位階層に書きすぎていない

### 良い状態
- リポジトリ共通ルール（言語、テスト、lint）はルートにある
- サブディレクトリ固有ルール（特定サービスの手順）はその配下にある
- 個人の好みは `~/.claude/CLAUDE.md` 等の個人設定側に寄せている

### NG 例
- 特定ディレクトリ専用ルールをルートに大量に書く
- 個人のエディタ好みやスタイル設定をチーム共有ファイルに書く
- フロントエンド固有のルールがバックエンドと同列に並んでいる

### スコープの判定基準

| ルールの種類 | 適切な配置場所 |
|------------|---------------|
| 全リポジトリ共通（言語、テスト、コミット規約） | ルート CLAUDE.md |
| 特定サービス/パッケージ固有 | サブディレクトリ CLAUDE.md |
| 個人の好み（出力スタイル、エディタ設定） | 個人設定ファイル |

## 5. 参照設計

### チェック項目
- [ ] `@` 参照や他ファイル参照が必要最小限か
- [ ] 毎回読む必要のない大きなドキュメントを常時参照させていないか
- [ ] 参照先の役割が明確か
- [ ] 参照指示が矛盾していないか

### 良い状態
- 毎回必要な最小限の参照だけがある
- 詳細な手順は Skill に分離されている
- 参照先ファイルの存在と役割が明確

### NG 例
- `docs/` 一式を丸ごと参照させる
- 毎回不要な長文仕様書を常時読むよう指示する
- 同じファイルに矛盾する参照条件を書く

#### 参照コスト

| 観点 | 見るポイント |
|------|--------------|
| 行数 | 参照先が長すぎないか |
| 数 | `@` 参照が多すぎないか |
| 再帰性 | 参照先がさらに参照を呼んでいないか |
| パスの必要性 | そのパスをエージェントが読む必要があるか、それとも人間向けの参考情報か |
| 読み込み指示の有無 | 「このファイルを読んでから作業する」等の指示がある場合、対象ファイルのサイズを確認 |

**改善パターン:**

| 現状 | 問題 | 改善案 |
|------|------|--------|
| `docs/` 配下の 10 ファイルを列挙 | エージェントが全部読みに行く | 必要なファイルだけに絞るか、「必要な場合のみ参照」と明記 |
| 「詳細は `docs/detailed-spec.md` を参照」 | エージェントが毎回読みに行く | Skill に移すか、要約をインラインに書く |
| ディレクトリパス `src/components/` | エージェントがディレクトリ探索を始める | 具体的なファイル名を示すか、探索が不要なら記載しない |

#### 参照コスト見積もりの手順

レビュー時に以下を確認する:

1. `@` インポートをすべて列挙し、各参照先の行数を確認する
2. 再帰的に展開される `@` がないか確認する（参照先にさらに `@` がある場合）
3. CLAUDE.md 本体 + 全 `@` 展開の合計行数を算出する
4. `@` なしのファイルパス記載を列挙し、エージェントが読みに行く可能性を評価する
5. 合計が 200 行を超える場合、または `@` が 3 件を超える場合は、分離の提案を行う

#### 参照整合性

同一ファイルへの参照指示が複数箇所にある場合、条件やトリガーが矛盾していないかを確認する。

| チェック項目 | 基準 |
|------------|------|
| 参照指示のトリガー条件が明確か | 「参照すること」=毎回か、特定条件時かを明記する |
| 同一ファイルへの参照が複数箇所にある場合、条件が一致しているか | A 節と B 節で異なる条件なら統一する |
| 参照指示が他セクションの制約と矛盾していないか | 「必ず読む」と「自動読み込みは CLAUDE.md に留める」が共存していないか |
| 参照先ファイルが実在するか | リンク切れがないか確認する |

**矛盾パターン例:**

| パターン | 例 | 問題 |
|---------|-----|------|
| 条件矛盾 | 「参照すること」vs「必要時に都度参照」 | エージェントがどちらに従うか不定 |
| 強度矛盾 | 「必ず読む」vs「自動読み込みは CLAUDE.md に留める」 | 制約が形骸化 |
| 暗黙の毎回読み込み | 条件なしの「XX.md を参照」 | 制約で抑制していても毎回読みに行く |

**改善パターン:**

| 現状 | 問題 | 改善案 |
|------|------|--------|
| 「ARCHITECTURE.md を参照すること」 | 毎回読み込みか条件付きか不明 | 「機能の実装場所が不明な場合は ARCHITECTURE.md を参照」 |
| A 節で「参照」B 節で「都度参照」 | 同一ファイルへの指示が矛盾 | 片方に統一し、もう片方は削除 |
| リンクあるが参照先が存在しない | リンク切れ | リンクを削除するか、ファイルを作成 |

## 6. ワークフローの明確さ

### チェック項目
- [ ] 作業開始時に何を確認するか書かれている
- [ ] 実装中・修正後に何を実行するか書かれている
- [ ] 作業完了の判定基準がある
- [ ] 手順の順序が明確

### 良い状態
- 開始: 「まず `CLAUDE.md` と関連ドキュメントを読む」
- 実装後: 「`npm test && npm run lint` を実行する」
- 完了: 「CI 全パス + レビュー指摘ゼロで Done」
- PR 前: 「差分を確認し、不要な変更が含まれていないことを確認する」

### NG 例
- 「必要なら確認」とだけ書かれている
- 手順の順序が曖昧で、何から始めるか分からない
- 実行コマンドが存在しない
