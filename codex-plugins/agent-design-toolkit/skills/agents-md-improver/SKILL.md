# AGENTS.md Improver

CLAUDE.md / AGENTS.md などのエージェント指示ファイルを、毎回読む価値のある内容だけに絞り、曖昧さがなく、遵守可否を後から検証できる形へ改善する。

## 重要方針

- 指示ファイルは「毎回読み込まれる常時コンテキスト」である前提でレビューする
- 能力紹介ではなく、エージェントが従う具体的な制約・手順・完了条件に絞る
- 曖昧語（「適切に」「丁寧に」「必要に応じて」「きれいに」）は検証可能な行動へ言い換える
- 毎回不要な詳細は Skill / subagent / 別ドキュメントへ逃がす
- 評価は 10 観点で行い、詳細基準は `references/review-checklist.md` を最優先にする

## 対象

- リポジトリルートの `CLAUDE.md` / `AGENTS.md`
- サブディレクトリ配下の `CLAUDE.md` / `AGENTS.md`（階層的スコープ）
- 個人設定の `CLAUDE.md`（`~/.claude/CLAUDE.md` 等、対象として渡された場合）
- これらが `@` 参照している指示系ファイル

## このスキルが重視する 10 観点

1. 役割分離 — 毎回読む価値がある内容だけか、特定タスク専用の長い手順が混ざっていないか
2. 指示の具体性 — 曖昧語に依存せず、誰が読んでも同じ行動を取れるか
3. 検証可能性 — 遵守可否・完了条件（Done の定義）・実行コマンドが明記されているか
4. スコープ設計 — グローバル / リポジトリ / サブディレクトリ / 個人設定の責務が分離されているか
5. 参照設計 — `@` 参照や他ファイル参照が最小限で、矛盾やリンク切れがないか
6. ワークフローの明確さ — 開始時・実装後・完了判定の手順と順序が明確か
7. 一貫性 — ルール間に矛盾や強度の食い違いがないか
8. 読み込みコスト — 冗長・重複・常時不要な長文がなく、トークン効率が良いか
9. スキル分解可能性 — 肥大化した手順を Skill / subagent に分離できないか
10. メンテナンス性 — 陳腐化しやすい記述や、更新ルールの欠如がないか

各観点の詳細なチェック項目・良い状態・NG 例は `references/review-checklist.md` を参照する。

## 手順

### 1. 対象ファイルを特定する

入力: ユーザー指定のパス、またはリポジトリ
出力: レビュー対象ファイルの一覧

- 対象が `CLAUDE.md` / `AGENTS.md` か確認する
- `SKILL.md` を渡された場合は対象外と報告し、`codex-skill-improver` を案内する
- subagent 定義（`agents/*.toml` 等）を渡された場合は `codex-subagent-improver` を案内する
- 対象ファイルが存在しない場合は、その旨を報告して終了する
- ルートだけでなく、サブディレクトリや `@` 参照先の指示ファイルも確認する

### 2. 現状の役割を短く要約する

入力: 対象ファイル
出力: 何を常時強制しているかの要約 2〜4 文

- 何を守らせ、いつ何を実行させ、何を Done とするかを読み取る
- 要約しづらい場合は、その時点で構造が曖昧だと判断する

### 3. 10 観点でレビューする

入力: 対象ファイル + `references/review-checklist.md`
出力: 観点ごとの問題一覧（重要度付き）

- 10 観点を順にチェックする
- `@` 参照は行数を見積もり、本体 + 全展開が 200 行超、または `@` が 3 件超なら分離を提案する
- 曖昧語を検出し、検証可能な行動への言い換え案を出す
- 300 行超、または特定タスク専用手順が長い場合は Skill / subagent への分離を提案する

### 4. 評価とレポートを出す

入力: 観点ごとの問題一覧
出力: 総合評価 + 重要度別レポート + 修正版

- 総合評価を A〜D で示す（A=良好 / B=軽微な改善 / C=要改善 / D=要全面改訂）
- findings は重要度順（高 / 中 / 低）に並べる
- 各 finding で「観点」「問題」「影響」「改善案」を短く示す
- 可能なら修正版をそのまま差し替えられる形で示す

## 出力ルール

- 構成は `## Findings`、`## 総合評価`、`## Revised File`、`## Residual Risks` の順を基本とする
- findings がない場合も、残るリスクと未検証項目は必ず書く
- 細かな文体指摘より、肥大化、曖昧さ、矛盾、検証不能、過剰な参照コストを優先する

## 補足

- 詳細なレビュー基準は `references/review-checklist.md` を参照する
- 発火テストと機能テストは `references/test-cases.md` を参照する
