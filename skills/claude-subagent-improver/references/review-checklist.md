# Claude Code サブエージェント定義レビュー観点

`claude-subagent-improver` を使うときは、共通観点で設計品質を確認した後、Claude Code 固有観点を追加で確認する。

## A. 共通レビュー

### A-1. 役割の明確さ

- 役割が単一責務に近いか
- 「何でも屋」になっていないか
- 親 agent や他 agent と責務が重複していないか
- 対象タスクが具体的に絞られているか

改善の方向:
- 役割が広すぎる定義は分割する
- 対象タスクを一言で説明できない定義は狭める

### A-2. 委譲条件の明確さ

- 「どんなときにこの agent を使うか」が明記されているか
- 能力紹介だけで終わっていないか
- 使わない場面も暗黙的に分かるか
- 他 agent と routing が衝突しないか

改善の方向:
- 対象タスク、呼び出し条件、避ける範囲を明示する
- 能力紹介文を routing 文へ書き換える

### A-3. 指示の自己完結性

- 役割が明示されているか
- 優先順位が明示されているか
- 禁止事項があるか
- 成功条件があるか
- 親の暗黙文脈に依存していないか

改善の方向:
- 職務、優先事項、禁止事項、完了条件、返却形式を追加する
- 「適切に」「必要に応じて」を具体化する

### A-4. 出力仕様の具体性

- 何を返すべきかが明確か
- 出力フォーマットが決まっているか
- severity / evidence / repro / impact などの粒度が明確か
- 何を優先して報告するかが示されているか

改善の方向:
- 出力順と必須項目を固定する
- findings の粒度を明示する

### A-5. 権限設計の妥当性

- 職務に対して必要最小限の権限か
- 調査役に不要な書き込み権限がないか
- reviewer に destructive な権限がないか
- 実行権限と責務が一致しているか

改善の方向:
- 役割に対して不要な権限を削る
- 読み取り中心か実行中心かを定義へ明記する

### A-6. モデル選択の妥当性

- 深い推論が必要な役割か
- 軽量モデルで十分な役割か
- 高コスト設定が過剰でないか
- 軽量すぎて品質不足にならないか

改善の方向:
- 重いレビューや設計判断には強いモデルを使う
- 単純な分類や探索は軽量モデルに落とす

### A-7. 保守性・可読性

- 長すぎないか
- 構造化されているか
- 更新しやすいか
- 同じ指示が重複していないか
- 上位 instruction と矛盾していないか

改善の方向:
- 重複した指示を削る
- 長い説明は構造化する

### A-8. sub-agent 化の妥当性

- 専門化の価値があるか
- 文脈分離のメリットがあるか
- 並列化で利益があるか
- 親が直接処理した方が自然ではないか

改善の方向:
- 分離価値が薄い役割は親へ戻す
- coordination cost が高い役割は切り出しを見直す

## B. Claude Code 固有レビュー

### B-1. Markdown + frontmatter としての定義の明確さ

- 必須フィールドが揃っているか
- frontmatter と本文の責務が混ざっていないか
- `description` と本文の役割分担が明確か
- Markdown 定義が読みづらい巨大プロンプトになっていないか

改善の方向:
- `description` は「いつ使うか」に寄せる
- 本文は「どう振る舞うか」に寄せる

### B-2. `description` の routing 品質

- 使用場面が明示されているか
- 能力説明だけで終わっていないか
- 他 agent と比較して境界が明確か
- trigger 条件が広すぎないか

改善の方向:
- 使用場面を具体化する
- オーバートリガーしやすい表現を削る

### B-3. system prompt の自己完結性

- 役割定義があるか
- 優先順位があるか
- 禁止事項があるか
- 何を報告すべきかがあるか
- 親の完全な system prompt がなくても成立するか

改善の方向:
- 行動単位で書く
- 完了条件と検証観点を足す

### B-4. `tools` / `disallowedTools` の境界

- 許可リストと拒否リストの使い分けが明確か
- 読み取り専用役に Write や Edit が残っていないか
- MCP ツールや Bash を安易に継承していないか
- `Agent(...)` を必要のない役割に付けていないか

改善の方向:
- 読み中心の役割は明示的な最小許可リストを優先する
- `disallowedTools` に頼りすぎず、境界を一目で分かる形にする

### B-5. 権限モードと実行制御

- `permissionMode` が役割に対して過剰でないか
- 親の権限継承と衝突しないか
- `maxTurns` が無駄に大きくないか
- `background` を本当に常時バックグラウンドで走らせる必要があるか

改善の方向:
- `bypassPermissions` は厳密な必要性がある場合に限る
- 長時間実行を前提にした設定は必要性を明示する

### B-6. `skills` / `mcpServers` / `memory` / `hooks` / `isolation` の妥当性

- `skills` が本当にプリロード必須な内容だけに絞られているか
- `mcpServers` が職務に必要なものだけか
- `memory` が継続学習の価値を持つ役割か
- `hooks` が条件付きルールとして整理されているか
- `isolation: worktree` が競合回避のために必要か

改善の方向:
- context 消費の大きい設定は明確な理由があるときだけ使う
- 便利そうだから足す、という設定追加を避ける

### B-7. built-in agent とメイン会話との境界

- built-in の Explore、Plan、General-purpose で足りない理由があるか
- メイン会話のまま進めた方が自然な作業を切り出していないか
- sub-agent 化の理由が context isolation、制約強制、再利用、コスト制御のいずれかで説明できるか

改善の方向:
- 既存機能で足りるなら custom sub-agent を増やさない
- 自己完結した作業だけを切り出す

### B-8. 再帰委譲の前提ミス

- sub-agent が他の sub-agent を生成できる前提で設計していないか
- 多段委譲を prompt で要求していないか
- parent 側の統合責務を sub-agent 側へ押し込んでいないか

改善の方向:
- サブエージェント内で完結する職務へ狭める
- 多段の調整はメイン会話または別機能へ戻す

## アンチパターン

- 役割が広すぎる
- `description` が能力紹介だけ
- system prompt が抽象的すぎる
- 出力要求がない
- 権限が過剰
- 親の暗黙文脈に依存している
- `skills` や `mcpServers` を盛り込みすぎている
- built-in agent で十分な役割を custom 化している
- sub-agent がさらに sub-agent を使う前提になっている

## レビュー出力テンプレート

```md
## Findings

1. [重大度] 問題の要約
   - 問題: 何が不足または過剰か
   - 影響: なぜ routing や品質が悪化するか
   - 改善: どう書き換えるか

## 改善案

- `description` の修正版
- system prompt の差し替え案
- 権限、モデル、frontmatter の見直し案

## 総評

- この定義で維持すべき強み
- 変更後に期待できる改善
```
