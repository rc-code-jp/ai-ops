# Codex サブエージェント定義レビュー観点

`codex-subagent-improver` を使うときは、共通観点で設計品質を確認した後、Codex 固有観点を追加で確認する。

## A. 共通レビュー

### A-1. 役割の明確さ

- 役割が単一責務に近いか
- 「何でも屋」になっていないか
- 親 agent や他 agent と責務が重複していないか
- 対象タスクが具体的に絞られているか

改善の方向:
- 役割が広すぎる定義は分割する
- 対象タスクを一言で説明できない定義は狭める

### A-2. 委譲条件の明確さ

- 「どんなときにこの agent を使うか」が明記されているか
- 能力紹介だけで終わっていないか
- 使わない場面も暗黙的に分かるか
- 他 agent と routing が衝突しないか

改善の方向:
- 対象タスク、呼び出し条件、避ける範囲を明示する
- 能力紹介文を routing 文へ書き換える

### A-3. 指示の自己完結性

- 役割が明示されているか
- 優先順位が明示されているか
- 禁止事項があるか
- 成功条件があるか
- 親の暗黙文脈に依存していないか

改善の方向:
- 職務、優先事項、禁止事項、完了条件、返却形式を追加する
- 「適切に」「必要に応じて」を具体化する

### A-4. 出力仕様の具体性

- 何を返すべきかが明確か
- 出力フォーマットが決まっているか
- severity / evidence / repro / impact などの粒度が明確か
- 何を優先して報告するかが示されているか

改善の方向:
- 出力順と必須項目を固定する
- findings の粒度を明示する

### A-5. 権限設計の妥当性

- 職務に対して必要最小限の権限か
- 調査役に不要な書き込み権限がないか
- reviewer に destructive な権限がないか
- 実行権限と責務が一致しているか

改善の方向:
- 役割に対して不要な権限を削る
- 読み取り中心か実行中心かを定義へ明記する

### A-6. モデル選択の妥当性

- 深い推論が必要な役割か
- 軽量モデルで十分な役割か
- 高コスト設定が過剰でないか
- 軽量すぎて品質不足にならないか

改善の方向:
- 重いレビューや設計判断には強いモデルを使う
- 単純な分類や探索は軽量モデルに落とす

### A-7. 保守性・可読性

- 長すぎないか
- 構造化されているか
- 更新しやすいか
- 同じ指示が重複していないか
- 上位 instruction と矛盾していないか

改善の方向:
- 重複した指示を削る
- 長い説明は構造化する

### A-8. subagent 化の妥当性

- 専門化の価値があるか
- 文脈分離のメリットがあるか
- 並列化で利益があるか
- 親が直接処理した方が自然ではないか

改善の方向:
- 分離価値が薄い役割は親へ戻す
- coordination cost が高い役割は切り出しを見直す

## B. Codex 固有レビュー

### B-1. TOML としての定義の明確さ

- 必須フィールドが揃っているか
- フィールドの責務が混ざっていないか
- `description` と `developer_instructions` の役割分担が明確か
- TOML 内で読みづらい巨大定義になっていないか

改善の方向:
- `description` は「いつ使うか」に寄せる
- `developer_instructions` は「どう振る舞うか」に寄せる

### B-2. `description` の routing 品質

- 使用場面が明示されているか
- 能力説明だけで終わっていないか
- 他 agent と比較して境界が明確か
- trigger 条件が広すぎないか

改善の方向:
- 使用場面を具体化する
- オーバートリガーしやすい表現を削る

### B-3. `developer_instructions` の具体性

- 役割定義があるか
- 優先順位があるか
- 禁止事項があるか
- 何を報告すべきかがあるか
- Done / Verify の考え方があるか

改善の方向:
- 行動単位で書く
- 完了条件と検証観点を足す

### B-4. `AGENTS.md` との整合性

- 上位の `AGENTS.md` と矛盾していないか
- 役割上必要な repo 文脈が上位で与えられているか
- subagent 側が上位 instruction を前提にしすぎていないか
- Done / Verify / Constraints の責務分担が崩れていないか

改善の方向:
- 上位に置くべき方針と agent 固有指示を分離する
- `AGENTS.md` 任せの曖昧さを減らす

### B-5. narrow and opinionated になっているか

- 役割が狭いか
- 判断軸がはっきりしているか
- output の傾向が安定しそうか
- 「広く支援する」系の曖昧さがないか

改善の方向:
- 判断軸を明示する
- 役割を限定して出力の傾向をそろえる

### B-6. 並列化・文脈分離との相性

- 読み中心タスクに向いているか
- write-heavy な競合タスクを無理に切り出していないか
- subagent 化の理由が context isolation か並列化かで説明できるか

改善の方向:
- 読み中心で独立した役割を優先する
- 競合しやすい write-heavy タスクは再検討する

## アンチパターン

- 役割が広すぎる
- `description` が能力紹介だけ
- `developer_instructions` が抽象的すぎる
- 出力要求がない
- 権限が過剰
- 親の暗黙文脈に依存している
- サブエージェント化が目的化している

## レビュー出力テンプレート

```md
## Findings

1. [重大度] 問題の要約
   - 問題: 何が不足または過剰か
   - 影響: なぜ routing や品質が悪化するか
   - 改善: どう書き換えるか

## 改善案

- `description` の修正版
- `developer_instructions` の差し替え案
- 権限またはモデルの見直し案

## 総評

- この定義で維持すべき強み
- 変更後に期待できる改善
```
