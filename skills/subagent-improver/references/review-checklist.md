# サブエージェント定義レビュー観点

`subagent-improver` を使うときは、まず以下の順で確認する。

## 1. 役割設計

- 単一責務か
- 親エージェントや他エージェントと境界が分かれているか
- 「何でもやる」定義になっていないか

改善の方向:
- 広い役割は分割する
- 専門性を一言で言えない定義は狭める

## 2. 委譲設計

- `description` や概要が「いつ使うか」になっているか
- 「得意」「支援する」だけで終わっていないか
- 使わない場面も推測できるか

改善の方向:
- 対象タスク、呼び出し条件、避けるべき範囲を明示する
- 能力紹介文を routing 文へ書き換える

## 3. 本文の自己完結性

- 本文だけで役割が理解できるか
- 優先順位があるか
- 禁止事項があるか
- 成功条件があるか
- 親の暗黙文脈に依存していないか

改善の方向:
- 職務、優先事項、禁止事項、完了条件、返却形式を追加する
- 「適切に」「必要に応じて」だけの文を具体化する

## 4. 出力仕様

- 何を返すかが具体か
- 重大度、根拠、影響範囲、再現条件などが必要なら指定されているか
- 些末な指摘より重要な問題を優先する設計か

改善の方向:
- 出力順と必須項目を固定する
- findings 形式、要約形式、提案粒度を定義する

## 5. 権限と安全性

- 役割に対して過剰なツール権限がないか
- reviewer や researcher に書き込み権限が不要ではないか
- destructive な操作が混じっていないか

改善の方向:
- 最小権限へ寄せる
- 読み取り専用で十分な役割は read-only にする

## 6. モデル選定

- 深い推論が必要か
- 低コストで足りるか
- 過剰な高性能モデルや不足した軽量モデルになっていないか

改善の方向:
- 重いレビューや設計判断には強いモデルを使う
- 単純な分類や探索は軽量モデルに落とす

## 7. 保守性

- 長すぎて要点が埋もれていないか
- 構造化されているか
- 更新しやすいか
- 上位 instruction と矛盾していないか

改善の方向:
- コア指示だけを本体に残し、詳細は別資料へ分離する
- 冗長な重複説明を削る

## 8. サブエージェント化の妥当性

- 文脈分離の価値があるか
- 並列化の価値があるか
- 強い逐次依存や同一文脈維持が必要な作業ではないか

改善の方向:
- 分離価値が薄いなら親エージェントに戻す
- 書き込み競合しやすい役割は安易に分割しない

## アンチパターン

- 役割が広すぎる
- `description` が能力紹介だけ
- 本文が抽象的すぎる
- 出力要求がない
- 権限が過剰
- 親の暗黙文脈に依存している
- サブエージェント化が目的化している

## レビュー出力テンプレート

```md
## Findings

1. [重大度] 問題の要約
   - 問題: 何が不足または過剰か
   - 影響: なぜ routing や品質が悪化するか
   - 改善: どう書き換えるか

## 改善案

- `description` の修正版
- 本文の差し替え案
- 権限またはモデルの見直し案

## 総評

- この定義で維持すべき強み
- 変更後に期待できる改善
- 残るリスク
```
