# Subagent Improver

サブエージェント定義を、実運用で安定して委譲される専門エージェントへ改善する。

## 基本方針

- 役割の広さより、委譲の正確さを優先する
- 定義ファイル単体で自己完結する状態を目指す
- スタイル改善より、ルーティング、出力品質、安全性、保守性を優先する
- Codex と Claude Code で形式が違っても、単一責務、明確な委譲条件、具体的な出力要求、最小権限の原則で統一して評価する

## 対象

- `subagent.md` のような設計メモや下調べ資料
- `AGENTS.md`
- `.codex/agents/*.toml`
- `.claude/agents/*.md`
- YAML frontmatter を持つエージェント定義 Markdown
- サブエージェントの役割や指示を説明する補助資料

## 手順

### 1. 対象と形式を特定する

- どのファイルがサブエージェント定義本体で、どのファイルが補助資料かを切り分ける
- Codex 形式か Claude Code 形式か、または設計メモかを判定する
- ファイルが複数ある場合は、委譲条件と本文の役割分担が分かる単位でまとめて読む

### 2. 現状の役割を要約する

- そのエージェントが何を担当し、いつ呼ばれる想定かを 2〜4 文で要約する
- 要約できない場合は、定義が曖昧だと判断する

### 3. レビューする

- `references/review-checklist.md` を使い、役割設計、委譲設計、本文の自己完結性、出力要求、権限、モデル、保守性、サブエージェント化の妥当性を確認する
- まず重大な欠陥を探す
- その後、発火精度や運用品質を下げる曖昧さを探す
- 最後に、冗長さや保守性の問題を拾う

### 4. 改善方針を決める

- 役割が広すぎる場合は分割を提案する
- `description` や委譲条件が弱い場合は、「何ができるか」ではなく「いつ使うか」に書き換える
- 本文が曖昧な場合は、優先順位、禁止事項、成功条件、返却形式を追加する
- 権限やモデルが過剰な場合は、必要最小限へ絞る
- サブエージェント化自体の価値が薄い場合は、親エージェントへ戻す案も出す

### 5. 修正版を提示する

- findings を重大度順に列挙する
- 各 finding で、問題、影響、改善方針を短く示す
- 可能なら修正版の定義文、`description`、本文、または差し替え案を提示する
- 変更後にどう改善されるかを 1 段落でまとめる

## 出力ルール

- findings を先に出す
- 軽微な文体指摘より、委譲失敗、責務衝突、出力不安定、安全性リスクを優先する
- 各 finding には、少なくとも「問題」と「なぜ悪いか」を含める
- 修正案はそのまま定義へ反映できる粒度で書く
- 問題がない場合も、残る運用リスクと検証不足を明示する

## 改善時の着眼点

- `description` は routing 文として読めるか
- 本文だけで、役割、優先順位、禁止事項、成功条件、返却形式が分かるか
- reviewer なのに編集権限を持つなど、役割と権限が食い違っていないか
- 深い推論が必要な役割に軽すぎるモデルを当てていないか
- その役割は本当にサブエージェントとして分離する価値があるか

## 補足

- 詳細なレビュー観点、アンチパターン、改善テンプレートは `references/review-checklist.md` を参照する
- 元資料が設計メモだけなら、その内容から「実際の定義へ落とすと何が必要か」を補って提案する
