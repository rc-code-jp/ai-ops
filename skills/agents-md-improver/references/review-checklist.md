# CLAUDE.md / AGENTS.md レビューチェックリスト

ステップ 2 の 10 観点レビューで使用する詳細基準。

---

## 1. 役割分離

### チェック項目
- [ ] 毎回読む価値がある内容だけに絞られている
- [ ] 特定タスク専用の長い手順（10 行超）が混ざっていない
- [ ] Skill / rules / subagent / 別ドキュメントに逃がすべき内容が残っていない

### 良い状態
- 常時守る制約、作業前提、完了条件だけがある
- 詳細なレビュー手順や特定技術の手順は別スキルに分離されている

### NG 例
- 特定フレームワークの詳細実装手順を長々と書く
- 毎回は不要な背景説明や設計思想が大量にある
- 特定の PR テンプレートや Markdown フォーマットが全文記載されている

---

## 2. 指示の具体性

### チェック項目
- [ ] 指示が具体的な行動として書かれている
- [ ] 曖昧語（「適切に」「丁寧に」「必要に応じて」「きれいに」）に依存していない
- [ ] 誰が読んでも同じ行動を取りやすい

### 良い状態の例
- 「変更後は `npm test` と `npm run lint` を実行する」
- 「新規依存追加は承認が必要」
- 「API 変更時は docs/ 配下も更新する」
- 「コミットメッセージは Conventional Commits 形式で書く」

### NG 例
- 「丁寧に対応する」
- 「必要に応じて確認する」
- 「適切にテストする」
- 「きれいなコードを書く」
- 「品質を保つ」

### 曖昧語の改善パターン

| 曖昧語 | 改善例 |
|--------|--------|
| 適切にテストする | `npm test` を実行し全件パスを確認する |
| 必要に応じて確認する | API 変更時は `docs/api.md` を更新する |
| 丁寧に対応する | エラー時は原因と対処を報告する |
| きれいなコードを書く | ESLint ルールに従い、警告 0 で通す |
| 品質を保つ | CI の全チェックがパスした状態で報告する |

## 3. 検証可能性

### チェック項目
- [ ] ルールの遵守可否を後から確認できる
- [ ] 成功条件・完了条件（Done の定義）が明記されている
- [ ] 実行すべきコマンドが具体的に書かれている
- [ ] 変更時に必ず更新するファイルやチェック項目がある

### 良い状態
- Done の定義: 「テスト全件パス + lint エラー 0 + 型チェック通過」
- 実行コマンド: `npm test && npm run lint && npm run typecheck`
- 更新ルール: 「API エンドポイント変更時は `openapi.yaml` も更新する」

### NG 例
- 完了条件がなく「終わったら報告」だけ
- 品質をどう確認するか不明
- 「テストを書く」とあるが何を確認するか未定義

## 4. スコープ設計

### チェック項目
- [ ] グローバル / リポジトリ / サブディレクトリの責務分離ができている
- [ ] 個人設定とチーム共通設定が混ざっていない
- [ ] 局所ルールを上位階層に書きすぎていない

### 良い状態
- リポジトリ共通ルール（言語、テスト、lint）はルートにある
- サブディレクトリ固有ルール（特定サービスの手順）はその配下にある
- 個人の好みは `~/.claude/CLAUDE.md` 等の個人設定側に寄せている

### NG 例
- 特定ディレクトリ専用ルールをルートに大量に書く
- 個人のエディタ好みやスタイル設定をチーム共有ファイルに書く
- フロントエンド固有のルールがバックエンドと同列に並んでいる

### スコープの判定基準

| ルールの種類 | 適切な配置場所 |
|------------|---------------|
| 全リポジトリ共通（言語、テスト、コミット規約） | ルート CLAUDE.md |
| 特定サービス/パッケージ固有 | サブディレクトリ CLAUDE.md |
| 個人の好み（出力言語、スタイル） | `~/.claude/CLAUDE.md` |
| 特定タスクの詳細手順 | Skill |

## 5. コンテキスト効率

### チェック項目
- [ ] 常時読み込む部分が 200 行以下（目安）
- [ ] 重要なルールが先頭に整理されている
- [ ] README や設計書の内容を重複して貼っていない
- [ ] 参照で済む内容はファイル名やパスだけ示している
- [ ] `@` インポートの数と参照先のサイズが適切か（下記「参照コスト」参照）
- [ ] ファイルパスの記載がエージェントの不要な読み込みを誘発していないか

### 良い状態
- 先頭に最重要ルール（禁止事項、完了条件、実行コマンド）がまとまっている
- 背景説明は最小限で、必要なら別ドキュメントへのリンクだけ
- 読む負荷が低く、スキャンしやすい構造
- `@` インポートは本当に毎回必要なものだけに絞られている
- 参照先ファイルは小さく、階層が浅い

### NG 例
- 背景説明が長く、実務ルールが埋もれている
- 例外や補足が多すぎて主ルールが見えない
- README やアーキテクチャドキュメントの内容を転記している
- 同じルールが表現を変えて複数回出てくる
- `@` インポートで大きなファイルや多数のファイルを読み込んでいる
- ファイルパスを大量に記載し、エージェントが片っ端から読みに行く

### コンテキストコストの目安

| 行数 | 評価 |
|------|------|
| 〜50 行 | 効率的。毎回読む負荷が低い |
| 50〜100 行 | 許容範囲。構造が整理されていれば問題なし |
| 100〜200 行 | 要注意。分離できる部分がないか確認 |
| 200 行超 | 要改善。スキル分解やサブディレクトリ分離を強く推奨 |

### 参照コスト

CLAUDE.md 内のファイル参照はコンテキストを膨張させる主要因である。以下の 2 種類を区別してレビューする。

#### `@` インポート（`@path/to/file.md`）

`@` インポートはセッション開始時に再帰的に展開され、**毎ターンのシステムプロンプトに全文注入される**。つまり参照先のファイルサイズがそのまま毎メッセージのトークンコストに加算される。再帰は最大 5 階層まで展開される。

| チェック項目 | 基準 |
|------------|------|
| `@` インポートの数 | 3 件以下が目安。多い場合は本当に毎回必要か確認 |
| 参照先ファイルのサイズ | 各 50 行以下が目安。大きい場合は要約版を作るか Skill に移す |
| 展開後の合計行数 | CLAUDE.md 本体 + 全 `@` 展開で 200 行以下が目安 |
| 再帰の深さ | 2 階層以下が望ましい。深い再帰はコストの見通しが悪くなる |
| 参照先の更新頻度 | 頻繁に変わるファイルを `@` で常時展開するのは非効率 |

**改善パターン:**

| 現状 | 問題 | 改善案 |
|------|------|--------|
| `@docs/architecture.md`（200 行） | 毎ターン 200 行分のトークンを消費 | 要約版（20 行）を作り `@docs/architecture-summary.md` を参照。または Skill に移し必要時だけ読む |
| `@` が 5 件以上 | 展開合計が膨大になりうる | 本当に毎回必要なものだけに絞る。残りは Skill か `.claude/rules/` に移す |
| `@a.md` → `@b.md` → `@c.md`（3 階層） | 展開コストの見通しが悪い | 階層を浅くし、直接参照に変える |

#### ファイルパスの記載（`@` なし）

`@` を付けずにファイルパスを記載した場合、自動展開はされないが、**エージェントがそのパスを認識して自主的にファイルを読みに行く可能性がある**。これは毎ターンではなく都度の読み込みだが、パスが多いとエージェントが不要なファイルまで読み込み、ツール呼び出し回数とコンテキストが増大する。

| チェック項目 | 基準 |
|------------|------|
| パスの記載数 | 多すぎないか（目安: 10 件以下）。本当に参照が必要なパスだけに絞る |
| パスの必要性 | そのパスをエージェントが読む必要があるか、それとも人間向けの参考情報か |
| 読み込み指示の有無 | 「このファイルを読んでから作業する」等の指示がある場合、対象ファイルのサイズを確認 |

**改善パターン:**

| 現状 | 問題 | 改善案 |
|------|------|--------|
| `docs/` 配下の 10 ファイルを列挙 | エージェントが全部読みに行く | 必要なファイルだけに絞るか、「必要な場合のみ参照」と明記 |
| 「詳細は `docs/detailed-spec.md` を参照」 | エージェントが毎回読みに行く | Skill に移すか、要約をインラインに書く |
| ディレクトリパス `src/components/` | エージェントがディレクトリ探索を始める | 具体的なファイル名を示すか、探索が不要なら記載しない |

#### 参照コスト見積もりの手順

レビュー時に以下を確認する:

1. `@` インポートをすべて列挙し、各参照先の行数を確認する
2. 再帰的に展開される `@` がないか確認する（参照先にさらに `@` がある場合）
3. CLAUDE.md 本体 + 全 `@` 展開の合計行数を算出する
4. `@` なしのファイルパス記載を列挙し、エージェントが読みに行く可能性を評価する
5. 合計が 200 行を超える場合、または `@` が 3 件を超える場合は、分離の提案を行う

## 6. ワークフローの明確さ

### チェック項目
- [ ] 作業開始時に何を確認するか書かれている
- [ ] 実装中・修正後に何を実行するか書かれている
- [ ] 作業完了の判定基準がある
- [ ] 手順の順序が明確

### 良い状態
- 開始: 「まず `CLAUDE.md` と関連ドキュメントを読む」
- 実装後: 「`npm test && npm run lint` を実行する」
- 完了: 「CI 全パス + レビュー指摘ゼロで Done」
- PR 前: 「差分を確認し、不要な変更が含まれていないことを確認する」

### NG 例
- 「必要なら確認」とだけ書かれている
- 手順の順序が曖昧で、何から始めるか分からない
- 実行コマンドが存在しない

---

## 7. 制約・禁止事項

### チェック項目
- [ ] やってはいけないことが明確に列挙されている
- [ ] 破壊的変更や本番影響のある操作に承認条件がある
- [ ] 自動変更の許容範囲が定義されている
- [ ] 秘密情報の取り扱いルールがある

### 良い状態
- 「本番設定変更は承認必須」
- 「DB マイグレーション追加時は事前確認」
- 「秘密情報は生成・保存・表示しない」
- 「外部依存の追加は承認が必要」
- 「`main` ブランチへの直接 push は禁止」

### NG 例
- 危険操作の境界がない
- 承認が必要なケースが分からない
- エージェントに過剰な裁量を渡している
- 「注意して操作する」とだけ書かれている

---

## 8. 出力期待値

### チェック項目
- [ ] エージェントに期待する報告形式が定義されている
- [ ] 作業結果の説明粒度が揃うようになっている
- [ ] 変更理由、影響範囲、未実施項目の扱いが明記されている

### 良い状態
- 報告に含める項目: 変更内容、実行したテスト結果、未対応の項目
- 実施済みと未実施を分けて報告する
- 影響範囲やリスクを明示する

### NG 例
- 何を報告すべきか不明
- 出力が毎回ぶれる（詳細だったり簡潔だったり）
- 実施済みと未実施が混ざる

---

## 9. スキル分解可能性

### チェック項目
- [ ] 10 行超の手順が Skill 化候補として存在する
- [ ] 役割別レビュー（セキュリティ、テスト等）が subagent 化候補として存在する
- [ ] 定型チェックが hook や script に移せる
- [ ] md 本体は短く、詳細は必要時だけ読む構成になっている

### 分解の判断基準

| 内容の性質 | 分解先 |
|-----------|--------|
| 特定タスクの詳細手順（10 行超） | Skill |
| 特定観点のレビュー手順 | subagent |
| 形式的な検証（lint、型チェック等） | hook / script |
| 特定ディレクトリ固有のルール | サブディレクトリ CLAUDE.md |
| 背景情報・設計判断の経緯 | 別ドキュメント（参照リンクのみ残す） |

### NG 例
- 何でも 1 ファイルに詰め込む
- 人が読まないと守れない定型ルールが多い（自動化すべき）
- タスク別知識の分離がない

## 10. 継続改善性

### チェック項目
- [ ] 再発ミスに対応した短い追記ができる構造になっている
- [ ] 重複したルールを統合しやすい
- [ ] ルール追加ばかりで肥大化していない
- [ ] 各ルールの目的が分かり、不要になったら削除できる

### 良い状態
- 再発ミスに対応した 1〜2 行の追記がしやすい
- セクション構造が明確で、どこに何があるか分かる
- 定期的に見直し・削除する前提がある

### NG 例
- 一度追加したルールが減らない（追記オンリー）
- 似た指示が何度も出てくる
- どのルールが効いているか分からない
- ルール同士が矛盾している
