# CLAUDE.md / AGENTS.md レビュー・改善ツール

AI エージェントが毎回読む指示ファイル（CLAUDE.md / AGENTS.md）を、最小コストで最大の行動精度を出せる運用契約へ改善する。

## 対象ユースケース

1. **既存の指示ファイルのレビュー**: 肥大化・曖昧化した CLAUDE.md / AGENTS.md の問題を検出し改善する
2. **新規の指示ファイルの品質チェック**: 作成直後のファイルがベストプラクティスに沿っているか検証する
3. **スキル分解の提案**: 長い手順や局所ルールを Skill / subagent / 別ファイルに分離する提案を行う

## 使う場面

- 「CLAUDE.md をレビューして」
- 「AGENTS.md を改善して」
- 「エージェント指示ファイルが長すぎるので見直して」
- 「指示が曖昧でエージェントの動きがブレる」

## 使用例

### 例 1: 曖昧な指示の改善

ユーザーの発話: 「CLAUDE.md をレビューして」

対象ファイルの状態:
```markdown
# ルール
- 丁寧に対応する
- 必要に応じてテストする
- きれいなコードを書く
```

検出される問題:
- 「丁寧に対応する」→ 行動として検証不可能
- 「必要に応じてテストする」→ 判断基準がない
- 「きれいなコードを書く」→ 定義が曖昧

改善案:
```markdown
# ルール
- 変更後は `npm test` と `npm run lint` を実行し、両方パスしてから報告する
- 新規関数には対応するテストファイルを追加する
- 変数名はキャメルケース、ファイル名はケバブケースを使う
```

### 例 2: 肥大化した指示ファイルのスキル分解

ユーザーの発話: 「AGENTS.md が長すぎるので整理して」

検出される問題:
- 毎回不要な詳細手順（セキュリティレビュー手順50行）が混在
- 特定ディレクトリ専用ルールがルートに大量にある
- README と重複する背景説明がある

改善案:
- セキュリティレビュー手順 → Skill に分離
- ディレクトリ固有ルール → サブディレクトリの CLAUDE.md に移動
- 背景説明 → 削除し、必要ならリンクだけ残す

## 手順

### ステップ 1: 対象ファイルの特定と読み込み

入力: ユーザーの指示（ファイルパス指定 or 「全部見て」等）
出力: 対象ファイル一覧と各ファイルの内容

1. ユーザーが指定したファイル、またはプロジェクト内の CLAUDE.md / AGENTS.md を探す
2. 一般的な配置場所を確認:
   - ルート `CLAUDE.md`
   - `.claude/CLAUDE.md`
   - サブディレクトリの `CLAUDE.md`
   - `AGENTS.md`（Codex 用）
3. 対象ファイルをすべて読み込む
4. ファイルが SKILL.md やサブエージェント定義の場合は対象外であることを報告する

### ステップ 2: 10 観点レビュー

入力: ステップ 1 のファイル内容
出力: 各観点の評価結果（問題リスト）

`references/review-checklist.md` の詳細基準に基づき、以下の 10 観点で評価する。各観点は「良い状態」との差分で問題を検出する。

| # | 観点 | 確認すること |
|---|------|-------------|
| 1 | 役割分離 | 毎回必要なルールだけに絞られているか。特定タスク専用の長い手順が混ざっていないか |
| 2 | 指示の具体性 | 行動として書かれているか。曖昧語（「適切に」「必要に応じて」）がないか |
| 3 | 検証可能性 | 完了条件、実行コマンド、チェック項目が明記されているか |
| 4 | スコープ設計 | グローバル/リポジトリ/サブディレクトリの責務分離ができているか |
| 5 | コンテキスト効率 | 長すぎないか。重要ルールが先頭にあるか。重複がないか |
| 6 | ワークフロー | 作業開始→実装中→完了の各段階で何をするか明記されているか |
| 7 | 制約・禁止事項 | 危険操作の境界と承認条件が明確か |
| 8 | 出力期待値 | 報告形式、説明粒度、未実施項目の扱いが定義されているか |
| 9 | スキル分解可能性 | 長い手順を Skill 化、定型チェックを hook/script 化できるか |
| 10 | 継続改善性 | ルール追加しやすく、削除もしやすい構造か |

#### 評価の優先順位

以下の順で重点的に確認する:

1. 毎回必要な最小限の内容に絞れているか（観点 1, 5）
2. 指示が具体的で検証可能か（観点 2, 3）
3. build/test/lint/Done が明記されているか（観点 3, 6）
4. 禁止事項と承認条件が明確か（観点 7）
5. 局所ルールを局所に置けているか（観点 4）
6. 重い手順を Skill に分離できているか（観点 9）

### ステップ 3: 減点ポイントの検出

入力: ステップ 2 の評価結果
出力: 減点ポイントの一覧（該当するものだけ）

以下に該当する場合は明示的に指摘する:

- 長すぎる（目安: 常時読み込む部分が 200 行超）
- 曖昧語が多い（「適切に」「丁寧に」「必要に応じて」）
- 背景説明が多すぎる（なぜこのルールがあるかの説明が本文を圧迫）
- README の重複が多い（別ドキュメントと同じ内容を転記）
- 個人設定と共有設定が混ざっている
- 完了条件がない
- 実行コマンドがない
- 禁止事項や承認条件がない
- 例外だらけで主ルールが見えない

### ステップ 4: 改善レポートの出力

入力: ステップ 2〜3 の全問題リスト
出力: 総合評価（A〜D）、問題一覧、改善案

以下の形式でレポートを出力する:

```
## CLAUDE.md レビュー結果: [ファイルパス]

### 総合評価: [A / B / C / D]

### 検出された問題

#### [重要度: 高/中/低] 問題タイトル
- 観点: [該当する観点番号と名前]
- 現状: ...
- 問題点: ...
- 改善案: ...

### 改善後のファイル案
(具体的な修正内容をコードブロックで提示)

### スキル分解の提案（該当する場合）
- [分離対象の内容] → [分離先（Skill / サブディレクトリ CLAUDE.md / hook 等）]
```

#### 総合評価の判定基準

| 評価 | 条件 | 意味 |
|---|---|---|
| A | 重要度「高」が 0 件、「中」が 1 件以下 | 運用可能。軽微な改善のみ |
| B | 重要度「高」が 0 件、「中」が 2 件以上 | 運用可能だが改善推奨 |
| C | 重要度「高」が 1〜2 件 | 改善しないと行動精度に影響 |
| D | 重要度「高」が 3 件以上 | 根本的な再設計が必要 |

#### 問題の重要度判定基準

| 重要度 | 基準 |
|---|---|
| 高 | エージェントの行動精度に直接影響する問題。曖昧な指示で毎回違う動きをする、禁止事項がなく危険操作を許容する、完了条件がなく作業が終わらない |
| 中 | 運用はできるが効率や品質が低下する問題。コンテキスト効率が悪い、スコープが不適切、スキル分解されていない |
| 低 | 改善の余地がある問題。構造の整理、重複の削除、表現の統一 |

レポートを出力した後、改善を実施するかユーザーに確認する。承認があるまでファイル編集は行わない。

### ステップ 5: 改善の実施

入力: ステップ 4 のレポート + ユーザーの承認（ステップ 4 末尾で取得）
出力: 編集済みファイル

1. ユーザーの承認を得たら、改善案に基づきファイルを編集する
2. スキル分解が提案された場合は、分離先のファイルも作成する
3. 編集後のファイルを表示して確認を促す

## テスト設計

発火テスト（5 件発火すべき + 5 件発火すべきでない）、機能テスト（正常系 3 件 + エラー系 2 件）、ベースライン比較は `references/test-cases.md` を参照。

## レビュー原則

- 長いことより、毎回効くことを優先する
- 方針より、行動を優先する
- 網羅より、常用性を優先する
- 詳細は Skill に逃がし、md 本体は薄く保つ
- 曖昧な善意ではなく、具体的な運用契約にする

## トラブルシューティング

### 対象ファイルが見つからない
原因: CLAUDE.md / AGENTS.md が標準的なパスに配置されていない。
解決策: ユーザーにファイルパスを確認する。プロジェクトルートから再帰的に検索する。

### 指示ファイルが極端に長い
原因: 役割分離とスキル分解が行われていない。
解決策: まず全体を読み込み、「毎回必要な部分」と「特定タスク専用の部分」に分類する。後者はスキル分解の提案に回す。

### レビュー対象が複数ある場合
原因: ルート + サブディレクトリに複数の CLAUDE.md がある。
解決策: まず一覧を提示し、ユーザーにレビュー対象を選択してもらう。スコープ設計（観点 4）の観点で、ファイル間の責務分離も評価する。
