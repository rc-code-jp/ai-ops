# Codex Skills ベストプラクティス詳細リファレンス

OpenAI の Codex Skills 公式ドキュメントを前提に、`codex-skill-improver` が参照する確認観点を整理したもの。

## 0. 最低限の仕様

Codex のスキルは、`SKILL.md` を必須とするディレクトリで構成する。任意で以下を持てる。

- `scripts/`: 決定的な検証や外部ツール連携
- `references/`: 長い説明、例、チェックリスト
- `assets/`: テンプレートや画像などの補助素材
- `agents/openai.yaml`: UI 情報、暗黙起動ポリシー、依存ツール

`SKILL.md` のフロントマター必須項目は次の 2 つ。

```yaml
---
name: skill-name
description: いつ使うか、いつ使わないかが分かる説明
---
```

## 1. `description` の評価軸

Codex では `description` が暗黙発火の主な判断材料になる。したがって、能力一覧ではなく routing 文として書く。

### 良い形

`[何をするか] + [いつ使うか] + [使わない場面 or 境界]`

例:

```yaml
description: Codex 用の SKILL.md をレビューし、description の発火境界、手順の明確さ、段階的開示、補助ファイル構成を改善する。スキルが暗黙発火しないとき、広すぎる責務を整理したいとき、Claude 前提のスキルを Codex に移植したいときに使う。一般的な Markdown 校正やコードレビューには使わない。
```

### 悪い形

- `スキルを改善する`:
  何をどう改善するか、いつ呼ぶかが不明
- `高品質なエージェントドキュメントを作る`:
  SKILL.md 専用か、AGENTS.md なのか、custom agent 定義なのかが不明
- `Claude / Codex / Cursor のスキルを全部見る`:
  対象が広すぎて暗黙発火境界を作れない

## 2. 1 スキル 1 責務

Codex 公式ドキュメントでは、各スキルを 1 つの仕事に集中させることが推奨される。

確認点:

- 単一のジョブとして 1 文で説明できるか
- 対象ファイル形式が散りすぎていないか
- 複数の改善対象がある場合、別スキルに分けるべきではないか

分割候補の例:

- SKILL.md 改善
- AGENTS.md 改善
- custom agent 定義改善

## 3. 指示は命令形で、入出力を明示する

Codex 向けの手順は、説明文よりも実行順序の明確さを優先する。

悪い例:

```md
必要に応じて構成を確認し、適切に修正する。
```

改善例:

```md
1. 対象ディレクトリ内の `SKILL.md` と `references/` を確認する
入力: スキルディレクトリ
出力: 構成一覧

2. `description` が暗黙発火境界として読めるか確認する
入力: `description`
出力: 発火上の問題一覧
```

## 4. 段階的開示

Codex はまず metadata を見て、必要時だけ `SKILL.md` 全文を読む。したがって、`SKILL.md` は短く保ち、詳細は `references/` へ分離する。

`SKILL.md` に残すもの:

- 重要方針
- 対象
- 手順
- 出力ルール

`references/` に逃がすもの:

- 詳細な観点一覧
- 多数の例
- テストケース集
- 長い背景説明

## 5. `scripts/` を使う基準

Codex 公式ドキュメントでは、まず instruction-only を基本とし、決定的な動作や外部ツールが必要な場合だけ script を追加する。

`scripts/` を使うべき例:

- YAML フロントマターの構文検証
- JSON Schema 検証
- 既知フォーマットへの変換

`scripts/` を使わなくてよい例:

- レビュー観点の列挙
- 発火境界の評価
- 文章の書き換え

## 6. `agents/openai.yaml` を使う基準

追加価値がある場合だけ提案する。

有効な用途:

- Codex app 向け表示名やアイコンを付けたい
- 暗黙起動を禁止し、明示呼び出し専用にしたい
- 依存する MCP / tools を宣言したい

不要な場合:

- 単純な instruction-only スキル
- UI 情報が不要な社内用スキル
- 依存ツールがないスキル

## 7. 発火テスト

最低でも以下を確認する。

- 発火すべき依頼: 5 件以上
- 発火すべきでない依頼: 5 件以上

見るポイント:

- 直接的な依頼で発火できるか
- 言い換え表現でも発火できるか
- 類似だが別スキルに寄せるべき依頼で誤発火しないか

## 8. よくある改善ポイント

- `description` が短すぎて発火条件が読めない
- スキル名とフォルダ名が一致しない
- `SKILL.md` 本文が長すぎて、コア手順より背景説明が目立つ
- 複数責務が混在している
- `scripts/` が不要なのに追加されている
- 逆に、構文検証が文章指示だけで済まされている

## 9. このスキルでのレビュー優先順

1. 暗黙発火の境界
2. 1 スキル 1 責務
3. 手順の命令形と入出力
4. 段階的開示
5. 補助ファイル構成の妥当性
6. 文体の細部
