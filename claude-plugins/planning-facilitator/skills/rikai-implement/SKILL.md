---
name: rikai-implement
description: 実装やファイル変更などの副作用ある操作を行う前に必ず発動し、ユーザーが実装内容を本当に理解しているかをテストしてから着手するゲートです。Edit / Write / NotebookEdit / 状態を変える Bash コマンド等を実行する直前、機能追加・修正・リファクタの依頼を受けた直後、計画を立て終わって実装フェーズに移ろうとするときに使います。ユーザーが「説明不要」「すぐ実装」「rikai スキップ」等で明示的にスキップを指示したターンと、純粋な調査・読み取り・質問応答だけで完結する場合には使いません。
---

### 1. 発動タイミングと適用範囲
副作用のある操作を行う直前に必ず発動してください。
対象は次のような操作です。
- ファイルの作成・編集（Edit / Write / NotebookEdit）
- 破壊的またはシステム状態を変える Bash コマンド（パッケージのインストール、マイグレーション、デプロイ、git push など）
- 設定ファイルや CI 設定、ホスト側設定の変更

純粋な調査・読み取り・質問応答だけで完結するターンでは発動しないでください。
ユーザーが「説明不要」「すぐ実装」「rikai スキップ」等を明示的に宣言したターンに限り省略できます。
そのスキップ宣言は当該ターンのみ有効で、次回以降に拡張解釈してはいけません。

### 2. 発動を宣言し、要点ブロックを提示する
発動したターンの最初に、次の発動宣言を 1 行出してください。
```
[rikai-implement] 実装前ゲートを発動します
```
これにより、ユーザーはゲートが効いていることを目視で確認できます。発動宣言を省略してはいけません。

続けて、実装方針を要点ブロックとして提示してください。
ただし、直前のターンで Plan Mode 等により承認済みの plan / 計画が存在する場合は、その要点をそのまま引用・要約して再掲してよく、ゼロから再生成する必要はありません。重複読みのコストを下げてください。

要点ブロックは次のテンプレートに揃えてください。
```markdown
### 要点
- **何を変える / 追加する**: 対象ファイル・関数・コマンド
- **なぜ**: 達成する状態・解決する課題
- **どう**: 採用するアプローチを 1〜3 行
- **副作用と影響範囲**: 壊れうる箇所、依存先、コマンドの実効果
- **スコープ外**: 今回はやらないこと
```

副作用欄に「特になし」とだけ書いてはいけません。
副作用が無いと判断した場合は、なぜ無いと判断したのかを 1 行で添えてください（例: 「呼び出し元のない純粋関数の追加のため副作用なし」「読み取り専用コマンドのため状態変更なし」）。

長文化させないでください。背景説明や設計談義を要点ブロックに混ぜてはいけません。
要点で伝わらない事項があれば、本文ではなく後段の質問または理解度テストで扱ってください。

### 3. 不明点があれば質問する
質問する前に、毎回次を確認してください。
1. コードベースや既存文脈を探索すれば分かるか。
2. 既存情報から妥当な前提として置けるか。
3. この回答で実装方針や提案内容が本当に変わるか。
4. これは今この時点で決める必要があるか。
1 または 2 で解決できるなら、まず自律的に補完してください。
3 が満たされないなら、その質問は省略してください。
4 が満たされないなら、後続フェーズに回してください。
質問するときは 1 ターン 1 判断とし、回答候補は番号付き＋自由入力併記で提示してください。

### 4. 理解度テストを実施する（このスキルの中核）
ユーザーから「OK」「進めて」とだけ言われた場合、それを GO サインにしないでください。
次のいずれかから **1〜2 問** を選び、ユーザー自身の言葉で回答してもらってください。
- **要約テスト**：「この実装をご自身の言葉で 1〜2 行で要約してください」
- **影響テスト**：「この変更によって既存の {具体機能 / フロー} の振る舞いはどう変わりますか」
- **境界テスト**：「もし {具体ケース} が来たら、この実装はどう動きますか」
- **副作用テスト**：「この変更で壊れうる箇所を 1 つ挙げてください」

テストはユーザーをからかうためではなく、**理解の解像度を共有する**ためのものです。
質問は丁寧かつ短く、ユーザーが答えやすい具体度で投げてください。
影響が極小な変更（設定ファイルの 1 行修正など）では 1 問で十分です。
広範囲・本番影響のある変更では 2 問に増やしてください。
抽象的な「分かりましたか？」は禁止です。

### 5. テスト結果に応じて分岐する
- 回答がズレている / 浅い場合：該当箇所を補足説明し、別の角度のテストを再実施してください。
- 回答が妥当な場合：「この方針で実装に着手してよいか」を最終確認し、GO サインを得てから実装フェーズへ移ってください。
- ユーザーが「テスト不要、進めて」と明示した場合：そのターン限定でテストを省略して構いません。
反論や追加注文が出た場合は、要点ブロックを修正してから再度テストしてください。

### 6. 禁止事項
- 理解度テストを通っていない状態で Edit / Write / 副作用のある Bash を実行しないでください。
- 「OK」「いいよ」だけを GO サインとして扱わないでください（理解の証拠が必要です）。
- スキップ宣言を勝手に拡大解釈しないでください（その時のみ有効です）。
- テストを尋問調・冗長にしないでください。
- 質問のための質問、枝葉の確認、表現を変えただけの再質問はしないでください。
- 質問より先に長い要件整理や結論一覧を出さないでください（要点ブロックで足りる範囲に留めてください）。

### 7. 完了条件と再発動
理解度テスト合格と最終 GO サインが揃ったら、ゲートを閉じて実装フェーズへ移ってください。
当初方針の範囲内の作業中は、毎ファイル・毎ステップで再発動しないでください。
ただし、実装中に方針を逸脱する判断（想定外の API 追加、設計の置き換え、影響範囲の拡張など）が必要になったら、その時点で再発動してください。
実装完了後に新たなバグ修正や追加要望を受けた場合は、別の変更として新規に発動してください。

---

### 要点
- 「説明 → 不明点解消 → 理解度テスト → 実装」の 4 段ゲートで動きます。
- 要点ブロックは短く、副作用とスコープ外を必ず含めます。
- 「OK」だけで通過させず、要約・影響・境界・副作用のいずれかで理解度を確認します。
- スキップは明示宣言があったターンのみ、当初方針逸脱時には再発動します。

### 使う場面
- 機能追加・修正・リファクタの実装に着手する直前。
- 設定ファイルやインフラ定義を書き換える直前。
- マイグレーションや本番影響のあるコマンドを実行する直前。
- 計画レビュー（Plan Mode 含む）が終わって実装フェーズに移行する瞬間。

### 例
良い例:
> [rikai-implement] 実装前ゲートを発動します
>
> ### 要点
> - **何を変える / 追加する**: `scripts/foo.sh` の 12 行目に `echo "done"` を追記
> - **なぜ**: ジョブ完了をログから検知できるようにするため
> - **どう**: 既存の最終行の直前に 1 行追加
> - **副作用と影響範囲**: 標準出力に 1 行増える。`done` をパースしている既存処理は無いことを確認済み
> - **スコープ外**: ログレベル分岐、別スクリプトへの展開
>
> 確認したいこと（境界テスト）：もしこのスクリプトが途中で `exit 1` した場合、追加した `echo "done"` は出力されますか？
>
> （ユーザー回答を待ち、合格なら「この方針で着手してよいですか」と最終確認してから Edit を呼ぶ）

悪い例:
> 「`scripts/foo.sh` を編集します。よろしいですか？」
> ユーザー「OK」
> （即 Edit を呼ぶ）

悪い例の問題:
- 要点ブロックが無く、副作用・スコープ外も伝えていません。
- 「OK」だけで GO サインにしており、理解度テストを通していません。
- ユーザーが意図しない箇所まで変更されても気付けません。
