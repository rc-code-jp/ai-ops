# HTML Plan

このスキルは、合意済みの実行プランを **読みやすい HTML ファイル** として `./plans/` 配下に書き出すためのものです。Markdown より目次・要点・ファイル一覧・検証手順を視覚的に追えるようにすることが目的です。

## 1. 発動条件と非発動条件

**発動するとき**(以下のいずれかをユーザーが明示的に指示したターンのみ)
- 「HTML でプランを出して / 書き出して / 保存して」
- 「html-plan で」「html-plan 発動」
- 「いまの計画を HTML にして」「プランを HTML ファイルにして」
- 上記に明確に類する表現

**発動しないとき**(以下では絶対に発動しない)
- Plan Mode を終了した直後の自動連動
- 他スキル(`rikai-implement` など)からの連鎖発動
- ユーザーが「プランを立てて」「計画して」と言っただけのターン(プラン提示は Markdown のままで良い)
- 調査・読み取り・質問応答だけで完結するターン

迷ったら発動しないでください。ユーザーが明示的に指示したかどうかが唯一の判断基準です。

## 2. 入力(プラン情報の抽出元)

次の優先順位で「現在のプラン」を特定します。
1. 直前のターンに `ExitPlanMode` で承認されたプラン本文
2. 会話中で直近に合意した実装計画(要点ブロック、TodoWrite の内容、ユーザーが OK を出した提案など)
3. それも見当たらない場合は、ユーザーに「どのプランを HTML 化しますか?」と 1 ターン 1 判断で確認

抽出する情報:
- **タイトル**: プランの主題を 1 行で
- **目的 / 背景**: なぜこの変更が必要か
- **要点**: 何を / なぜ / どう / 副作用 / スコープ外
- **ファイル変更一覧**: path / 操作(add / edit / delete) / 概要
- **実装ステップ**: 順序、各ステップの目的と完了条件
- **検証手順**: 動作確認・テスト・受け入れ条件
- **メタ情報**: 生成日時、対象リポジトリ / ブランチ

## 3. 出力ファイル名規則

- 配置先: 作業中リポジトリのルート相対 `./plans/`
- ファイル名: `plan-YYYY-MM-DD-{slug}.html`
  - `YYYY-MM-DD` は本日の日付
  - `slug` は kebab-case、英数字とハイフンのみ、最大 40 文字
  - 日本語タイトルは英訳または音写してから kebab-case 化する
- 衝突時: 同一日に同名ファイルがある場合 `-2`, `-3` … を末尾に付与
- `./plans/` ディレクトリが存在しなければ作成する

例: `./plans/plan-2026-05-11-add-html-plan-skill.html`

## 4. HTML の組み立て手順

1. このスキルと同階層の `references/template.html` を Read する
2. 以下のプレースホルダを抽出した情報で置換する
   - `{{TITLE}}` — プランタイトル
   - `{{GENERATED_AT}}` — 生成日時(ISO 8601 形式と人間向け表記の両方)
   - `{{REPO}}` — リポジトリ名(`git remote get-url origin` などから取得、不明なら空)
   - `{{BRANCH}}` — 現在のブランチ名(`git branch --show-current`、不明なら空)
   - `{{TOC}}` — 目次(各 `<section id="...">` に対応する `<a>` リンク)
   - `{{SUMMARY_WHAT}}` / `{{SUMMARY_WHY}}` / `{{SUMMARY_HOW}}` / `{{SUMMARY_SIDE_EFFECTS}}` / `{{SUMMARY_OUT_OF_SCOPE}}` — 要点ブロック各項
   - `{{FILES_TABLE}}` — ファイル変更一覧の `<tr>` 行群
   - `{{STEPS}}` — 実装ステップの `<li>` 群
   - `{{VERIFICATION}}` — 検証手順の `<li>` 群(チェックボックス `☐` 文字を行頭に置く)
   - `{{META}}` — フッターのメタ情報(スキル名、バージョン)
3. 置換結果を `./plans/plan-YYYY-MM-DD-{slug}.html` へ Write する
4. ユーザーに保存パスを報告する。長文プランの場合でも、本文を会話に再掲する必要はない(ファイルパスだけ伝える)

## 5. スタイル方針(テンプレート側で守る)

- `<style>` は `<head>` 内にインライン。外部 CSS / CDN は使わない
- 外部 JS、`<script>` タグは一切埋め込まない
- フォントは `system-ui, -apple-system, "Segoe UI", "Hiragino Sans", "Yu Gothic", sans-serif`
- `body { max-width: 760px; margin: 0 auto; line-height: 1.7; }`
- `@media (prefers-color-scheme: dark)` でダークパレットに切り替え
- `@media print` で目次 `<nav>` を非表示にし、A4 印刷 / PDF 出力に耐えるようにする
- 色数は抑える(本文 / 強調 / 罫線 / 背景の 4 色程度)

## 6. 禁止事項

- `./plans/` 以外への HTML 書き込み(他ディレクトリへの保存禁止)
- HTML 内への `<script>` 埋め込み、`onload` などのイベントハンドラ
- 外部 CDN(Google Fonts、Tailwind CDN、Mermaid CDN など)への参照
- Plan Mode 終了や他スキル発動に紐づく自動発動
- ユーザーが明示指示していないのに「ついでに HTML でも出しておきますね」と先回りすること
- プラン内容を勝手に書き換える / 追加で考察を入れる(忠実な可視化に徹する)

## 7. 使う場面

- Plan Mode で合意したプランを後でブラウザでレビューしたい
- 非エンジニアや別チームにプラン内容を共有したい
- 印刷 / PDF として保存しておきたい
- 長大なプランを目次付きで眺めたい

### 例

良い例:
> ユーザー: 「いまのプランを HTML で出して」
>
> アシスタント: (`references/template.html` を Read → 置換 → `./plans/plan-2026-05-11-add-html-plan-skill.html` へ Write)
> 「`./plans/plan-2026-05-11-add-html-plan-skill.html` に書き出しました。ブラウザで開いてご確認ください。」

悪い例:
> ユーザー: 「プランを立てて」
>
> アシスタント: (Markdown でプランを提示したあと、聞かれていないのに HTML ファイルも生成する)

悪い例の問題:
- ユーザーは明示的に HTML 出力を指示していない
- 自動発動はこのスキルの禁止事項に該当する
- 不要なファイルが `./plans/` 配下に増えていく
