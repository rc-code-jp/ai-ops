# HTML Doc

このスキルは、仕様書・設計書・計画資料・プロジェクト説明資料などのドキュメントを **人間が読みやすい HTML ファイル** として書き出すためのものです。表紙・目次・章単位の改ページを備え、ブラウザから PDF 印刷した際に **ページ単位でも見やすい** ことを目的とします。

CSS / スタイルはスキル同梱のテンプレートに固定されており、生成のたびに CSS を書き起こすことはしません。本文は同梱のコンポーネントカタログ（フロー図・タイムライン・ガント・カード・表など）の部品を組み合わせて構成し、**フロー・スケジュール・体制・数値はなるべく視覚的に表現** します。

**ユーザーは生成された HTML を見ながら、修正依頼を繰り返します。** 反復生成と長大ドキュメントに耐えるよう、HTML の組み立てはサブエージェントに委任します。

## 1. 発動条件と非発動条件

**発動するとき**（以下のいずれかをユーザーが明示的に指示したターンのみ）
- 「HTML でドキュメント / 仕様書 / 設計書 / 計画資料 / 説明資料を作って・出して・書き出して」
- 「html-doc で」「html-doc 発動」
- 「この内容（仕様・計画）を HTML にして」「HTML ドキュメントにまとめて」
- 上記に明確に類する表現

**発動しないとき**（以下では絶対に発動しない）
- 他スキル（`html-plan` など）からの連鎖発動
- ユーザーが「仕様をまとめて」「ドキュメントを書いて」と言っただけのターン（Markdown での提示で良い）
- 調査・読み取り・質問応答・コード実装だけで完結するターン
- 実行プランの HTML 化（それは `html-plan` スキルの領分）

迷ったら発動しないでください。ユーザーが明示的に指示したかどうかが唯一の判断基準です。

## 2. 動作モデル（委任型）

このスキルは **親 Claude → サブエージェント** の二段構成で動きます。

```
[親 Claude]                       [サブエージェント (general-purpose)]
 │ ① ドキュメント化する内容を特定
 │ ② メタ情報(タイトル, 種別, 版数等)を決定
 │ ③ 出力先とファイル名を決定
 │ ④ Agent ツールで起動 ─────────► プロンプト受領
 │                                 │ ⑤ template.html / components.md を Read
 │                                 │ ⑥ メタ置換 + {{BODY}} を部品で組み立て
 │                                 │ ⑦ 出力先へ Write
 │ ⑧ 保存パスだけ受け取る ◄────── 戻り値: 保存パス(短文)
 │ ⑨ ユーザーに保存パスを伝える
```

委任する理由:
- 生成 HTML 全文（数 KB 〜 数十 KB）を親会話履歴に残さないため
- 反復的な再生成（修正→再 HTML 化）で親コンテキストが累積しないため
- 長大なドキュメントでもメイン推論を圧迫しないため

**親 Claude がやってはいけないこと**: 自分で `template.html` や `components.md` を Read したり、自分で `Write` を呼んだりしないでください。必ずサブエージェントに委任します（理由: そうしないと HTML 全文が親履歴に残るため）。

## 3. 親 Claude の手順

### 3.1 入力（ドキュメント化する内容）の特定

次の優先順位で「対象の内容」を特定します。
1. ユーザーがこのターンで提示した文章・ファイル・会話中の合意内容
2. 会話中で直近にまとめた仕様・計画・説明の本文
3. それも見当たらない場合は、ユーザーに「どの内容を HTML ドキュメント化しますか?」と 1 ターン 1 判断で確認

### 3.2 メタ情報の決定

会話内容から以下を決めます。不明なものはユーザーに確認せず妥当な値を採用します（VERSION 不明なら「v1.0」、AUTHOR 不明なら「-」）。

- TITLE: ドキュメントタイトルを 1 行で
- SUBTITLE: サブタイトル（無ければ空）
- DOC_TYPE: 文書種別（例: 仕様書 / 設計書 / 計画資料 / 説明資料 / 手順書 / 提案書）
- VERSION: 版数（例: v1.0、第 2 版）
- DATE: 本日（`YYYY-MM-DD`）
- AUTHOR: 作成者（ユーザーが指定した場合のみ。無ければ "-"）

### 3.3 出力先とファイル名の決定

- 配置先: **ユーザーが指定したパスを最優先**。指定が無ければ作業中リポジトリのルート相対 `./docs/`（無ければ作成）
- ファイル名: `doc-YYYY-MM-DD-{slug}.html`
  - `slug` は kebab-case、英数字とハイフンのみ、最大 40 文字
  - 日本語タイトルは英訳または音写して kebab-case 化
  - ユーザーがファイル名まで指定した場合はそれに従う
- **反復生成時の上書きルール**: 同一日に **同じ slug** のファイルがあれば **上書き** する（修正→再生成のため）。slug が変われば別ファイルとして併存
- 明示的に「別ファイルとして残して」と言われた場合のみ `-2`, `-3` を末尾に付与

### 3.4 テンプレートとカタログの絶対パス解決

サブエージェントは親 Claude と独立したワーキングディレクトリを持つため、参照ファイルは **絶対パス** で渡す必要があります。

テンプレートとカタログは、この **SKILL.md と同じディレクトリの `references/`** に置かれています。
- `references/template.html` — HTML 外枠 + 全コンポーネント CSS
- `references/components.md` — 本文に使える部品のカタログ

解決手順（上から優先）:
1. 環境変数 `CLAUDE_PLUGIN_ROOT` が定義されていれば → `${CLAUDE_PLUGIN_ROOT}/skills/html-doc/references/...`
2. SKILL.md 自身の絶対パスから導出 → `<SKILL.md と同じディレクトリ>/references/...`
3. それも不明な場合のみ最後の手段として `find ~/.claude -path '*html-doc/references/template.html' -print -quit` 等で探索

この 2 つの絶対パス（以下 `{TEMPLATE_ABS_PATH}` / `{CATALOG_ABS_PATH}`）を 3.5 でサブエージェントに渡します。

### 3.5 サブエージェントへの委任

`Agent` ツールで `general-purpose` サブエージェントを 1 つ起動します。プロンプトは次のテンプレートに揃えてください。

```
あなたは「html-doc」スキルのレンダリング担当サブエージェントです。
親 Claude のメインコンテキストを汚さないため、HTML の組み立てと書き出しを引き受けます。

## やること
1. テンプレートを Read（絶対パス）: {TEMPLATE_ABS_PATH}
2. コンポーネントカタログを Read（絶対パス）: {CATALOG_ABS_PATH}
3. 下記「ドキュメント本文」を章立てし、テンプレート内のプレースホルダを置換
4. {{BODY}} はカタログの部品だけで組み立てる
5. 出力先へ Write: {OUTPUT_PATH}
6. 戻り値は「保存パス（と必要なら 1〜2 行のサマリ）だけ」。HTML 本文は絶対に出力に含めないこと

## プレースホルダ対応
- {{TITLE}}      {TITLE}
- {{SUBTITLE}}   {SUBTITLE}（空なら空文字で置換）
- {{DOC_TYPE}}   {DOC_TYPE}
- {{VERSION}}    {VERSION}
- {{DATE}}       {DATE}
- {{AUTHOR}}     {AUTHOR}
- {{TOC}}        <li><a href="#sec-N">章タイトル</a></li> を章の数だけ。
                 テンプレート内に {{TOC}} は 2 箇所ある（印刷用目次・画面用サイドバー）。両方に同じ内容を入れる
- {{BODY}}       本文 HTML 断片（下記の組み立て方針に従う）
- {{META}}       フッター用の補足（例: "Generated by html-doc skill"）

## {{BODY}} の組み立て方針
- 章は <section class="chapter" id="sec-N"><h2 class="chapter-heading">N. タイトル</h2>...</section>。
  id は {{TOC}} のアンカーと一致させる。章番号はタイトル文字列に含める
- 印刷時は章ごとに改ページされる。1 章が A4 で 1〜3 ページに収まる粒度に章を分ける
- **視覚優先**: フロー・手順はフロー図(.flow)や手順リスト(.procedure-steps)、
  スケジュールはタイムライン(.timeline)やガント(.gantt)、体制・機能一覧はカード(.card-grid)、
  規模・KPI は数値ハイライト(.stat-grid)、比較・一覧は表(.doc-table)で表現する。
  段落だけが続く章を作らない
- 注意点・制約はコールアウト(.callout--info/--warning/--danger/--success)で目立たせる
- 仕様書・計画資料では改訂履歴(.revision-table)の章を末尾に置く（履歴情報が無ければ初版 1 行）
- 使える部品・マークアップはカタログ（components.md）に厳密に従う。カタログに無いクラスを発明しない

## 制約
- テンプレ内の <style> 領域は改変しない（プレースホルダ部分のみ置換）
- HTML エスケープを徹底（<, >, &, ", ' を実体参照に）。`<code>` 内も同様
- 外部 CDN や <script> は追加しない
- ドキュメント内容を要約・脚色しない（忠実に構成し直すのは可、内容の改変は不可）
- 出力ディレクトリが無ければ作成
- 最終応答は「保存パス: {OUTPUT_PATH}」のみ（HTML 全文を返さない）

## メタ情報
- OUTPUT_PATH: {OUTPUT_PATH}

## ドキュメント本文（HTML 化する対象）
---
{DOC_BODY}
---
```

差し込む値:
- `{TEMPLATE_ABS_PATH}` / `{CATALOG_ABS_PATH}` — 3.4 で解決した絶対パス
- `{TITLE}` / `{SUBTITLE}` / `{DOC_TYPE}` / `{VERSION}` / `{DATE}` / `{AUTHOR}` — 3.2 で決めた値
- `{OUTPUT_PATH}` — 3.3 で決めた値
- `{DOC_BODY}` — 3.1 で特定した内容を **そのまま** 貼る（要約しない）

### 3.6 戻り値の取り扱い

サブエージェントは「保存パス」と短いサマリだけ返してきます。親 Claude はこれをユーザーに伝えるだけにしてください。

良い報告例:
> `./docs/doc-2026-06-05-payment-spec.html` に書き出しました。ブラウザで開き、PDF にする場合は印刷（Cmd+P / Ctrl+P）から「PDF に保存」してください。

悪い報告例:
- 生成された HTML の中身を会話に貼り直す
- ドキュメント本文を再掲する
- サブエージェントが返した説明を長々と転記する

## 4. 反復的なドキュメント修正への対応

ユーザーは HTML を見ながら以下を行うことが想定されます。

- 「この章を書き換えて」「スケジュールをガントにして」など部分修正
- 「注意書きを追加して」などの追記
- 「もう一度 HTML にして」と再生成

このとき親 Claude は:
1. まず会話上でドキュメント内容を更新する
2. 「もう一度 HTML にして」と言われたら、最新の内容を持って 3.5 のサブエージェント起動を再実行
3. 同日同 slug のファイルは上書きする（3.3 の上書きルール）

サブエージェントは毎回新規に起動して構いません（状態を持たない）。親会話には HTML 全文が残らないため、何度反復しても親コンテキストは膨れません。

## 5. 禁止事項

- **親 Claude が直接 `template.html` / `components.md` を Read したり、`Write` で HTML を書き出すこと**（必ずサブエージェント経由）
- サブエージェントの戻り値として HTML 全文を親会話に持ち帰ること
- HTML 内への `<script>` 埋め込み、`onload` などのイベントハンドラ
- 外部 CDN（Google Fonts、Tailwind CDN、Mermaid CDN など）への参照
- 他スキル発動に紐づく自動発動、ユーザーが明示指示していないのに先回りで HTML 出力すること
- ドキュメント内容を勝手に書き換える / 追加で考察を入れる（忠実な可視化に徹する）

## 6. 使う場面

- まとめた仕様・設計を関係者にレビューしてもらいたい
- 計画資料・プロジェクト説明資料を非エンジニアに共有したい
- 印刷 / PDF として配布・保存したい（ページ単位で読みやすい）
- フローやスケジュールを視覚的に見せたい
- ドキュメントを反復的に修正しながら HTML を更新したい

### 例

良い例:
> ユーザー: 「この仕様を html-doc で HTML にして」
>
> アシスタント:
> （Agent ツールで general-purpose サブエージェントを起動。プロンプトに 3.5 のテンプレを使い、仕様本文を埋め込む）
>
> サブエージェント: `保存しました: ./docs/doc-2026-06-05-auth-spec.html`
>
> アシスタント:
> 「`./docs/doc-2026-06-05-auth-spec.html` に書き出しました。ブラウザで開いてご確認ください。」

良い例（反復修正）:
> ユーザー: 「スケジュール章をガントチャートにして、もう一度 HTML にして」
>
> アシスタント:
> （会話上で内容を更新 → 再びサブエージェントを起動 → 同 slug を上書き）
> 「同じパスに上書きしました: `./docs/doc-2026-06-05-auth-spec.html`」

悪い例（直接 Write）:
> ユーザー: 「HTML で出して」
>
> アシスタント: （自分で `template.html` を Read して置換し、自分で Write を呼ぶ）
>
> 問題: HTML 全文が親会話履歴に残り、その後の反復で累積する。長大なドキュメントや繰り返し編集でメインコンテキストを圧迫する。

悪い例（自動発動）:
> ユーザー: 「仕様をまとめて」
>
> アシスタント: （Markdown で仕様を提示したあと、聞かれていないのに HTML ファイルも生成する）
>
> 問題: ユーザーが明示指示していないのに発動しており、本スキルの禁止事項に該当。
